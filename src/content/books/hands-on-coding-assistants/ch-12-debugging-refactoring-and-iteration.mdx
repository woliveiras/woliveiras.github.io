## Start at the first incorrect observation

Suppose a valid registration returns ID `2` after a rejected request. The caller sees a 400 for the rejected request, so an assertion about status alone would miss the problem. The failing ID check gives you a concrete place to start tracing.

Run `npm run test:registration`. Give **Plan** the failing assertion, the file `contracts/registration.test.ts`, and the route in `src/app.ts`. Ask it to follow data from the request, through normalization and validation, to ID assignment and the array push. Ask which statement could explain the observed ID.

When the agent suggests a fix, compare it with that trace. A small move in the handler may be enough. If the explanation depends on another API or a database, ask it to point to the line. The lab stores registrations in memory, and the HTTP test starts a fresh server for each case.

## Refactor after you have a green baseline

On a branch with [the registration change](/books/hands-on-coding-assistants/chapters/the-spec-first-workflow/) complete, extract registration validation into a function that takes an unknown input and returns normalized strings or no value. The route should still own the status code, ID allocation, and state change.

```text
Propose a behavior-preserving refactor of the registration validation.
Keep the existing HTTP contract and storage. Name the existing tests
that would catch a change in behavior. Stop after a small diff.
```

Review the plan, then implement or ask **Build** to apply it. Run:

```sh
npm test
npm run test:registration
git diff --check
git diff -- src/app.ts
```

Compare where validation happens before and after the refactor. If the extracted function allocates an ID or pushes to the array, the change crosses the boundary you set. If the helper is called from one place and makes the route harder to follow, keeping the code inline remains a reasonable decision.

## Make the handoff about facts

If you need a new session, write the branch, the failing assertion or current verified state, the files changed, and the remaining decision. Include the last verification command and its observed result. Ask the next session to read the diff before proposing anything.

A handoff can also be a good place to switch models. Both routes run the same checked-in commands, so the new model can recover from the state of the project even when it has none of the earlier conversation.
