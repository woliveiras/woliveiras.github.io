## Start at the first incorrect observation

The registration spec says that rejecting a request leaves the next ID available. Yet the first valid request after a rejection can return ID `"2"`. Both status codes look right. You need the sequence to see the failure.

Use the `lab-debugging` tag, which starts from a working registration change and reintroduces the bug. Commit any previous exercise first. From the lab root, create the branch and run the starter suite and the contract separately.

```sh
git switch -c debug-registration lab-debugging
mkdir -p notes
npm test
npm run test:registration
```

The base suite passes. In the registration contract, the normalization test passes and the other test expects ID `"1"` after 14 rejections. It gets `"15"`. Try just one rejection and one success against the same fresh server. Start it with `PORT=3100 npm start`, then run both requests in a second terminal.

```sh
curl -sSi http://127.0.0.1:3100/registrations \
  -H 'Content-Type: application/json' \
  -d '{"name":42,"email":"ada@example.test"}'
curl -sSi http://127.0.0.1:3100/registrations \
  -H 'Content-Type: application/json' \
  -d '{"name":"Ada","email":"ada@example.test"}'
```

Expect `400` and `{"error":"invalid_registration"}`, then `201` and `{"id":"2","name":"Ada","email":"ada@example.test"}`. Restart the server when you need to try the sequence from ID `"1"`. Stop it when you're done.

## Test the explanation before asking for an edit

Run `opencode` in the lab root, start a fresh session with `/new` if needed, and select **Plan** with `/agents`. Give it the responses you observed and one question it can trace.

```text
On a fresh server a numeric name gets HTTP 400. The following valid
registration gets HTTP 201 with id "2". Read specs/registration-validation.md,
contracts/registration.test.ts and src/app.ts. Trace both requests.
Check these possible causes against the code and evidence: an incorrect
initial value, an extra stored registration, or allocation on rejection.
Cite the relevant statements and tell me what you can rule out.
Return findings for review before proposing an edit.
```

On another fresh instance, try a valid request first. It gets ID `"1"`, which rules out an incorrect initial value. The rejected request returns before the array push. Inspect the statement that advances the counter and see whether execution reaches it before that return. You can make the fix as small as the cause.

## Prove the failure in a focused test

Switch to **Build** in the same session after you've checked the cause. Ask for the test first.

```text
Add test/registration-regression.test.ts using startApp(t) and
jsonRequest from test/client.ts. Send the two inputs we reproduced,
in order, to one fresh server. Assert 400 and invalid_registration
for the numeric name, then 201 and ID "1" for the valid request.
Leave src/app.ts unchanged. Run the focused test and show where it fails.
```

```sh
node --test test/registration-regression.test.ts
```

Read the failure. A test that only sees `400` would pass this broken implementation. Once you can reproduce the `"2"` result with the new test, give Build the failing assertion and ask for the smallest correction.

```text
The focused test gets ID "2" after a rejected request. In src/app.ts,
move ID allocation after validation succeeds. Preserve the accepted
response and the test assertions. Run the focused test, npm test,
and npm run test:registration and report each result.
```

Inspect the diff and rerun the test and both suites.

```sh
node --test test/registration-regression.test.ts
npm test
npm run test:registration
git diff --check
git status --short
```

Expect all tests to pass. Check the changed handler and read the new file as well. Git does not include an untracked test in `git diff` until you stage it.

## Make the handoff about facts

Give Build the original and corrected results and ask it to save the handoff.

```text
Write notes/registration-fix.md using the responses and test results
I checked. Record the symptom, shortest reproduction, cause, focused
change, and both results of the regression test. Name the base tag
lab-debugging and the commands a reviewer can rerun. Write only the note.
```

Check the note against your observations. Commit it with the fix and test so someone can compare the result against the fixture.

```sh
git add src/app.ts test/registration-regression.test.ts notes/registration-fix.md
git diff --cached --check
git diff --cached --stat
git commit -m "Preserve the next registration ID after rejection"
```

## Refactor after you have a green baseline

With the fix committed, you can try extracting a validation function in a separate branch. Keep status codes, ID allocation and storage in the route. Rerun the focused test and the contract after the extraction. Leave the function inline if extracting it makes the order harder to see.

Use the branch with the verified fix to [break down the task labels epic](/books/hands-on-coding-assistants/chapters/break-down-an-epic/). Its plan and the API documentation that follows both start from that version of the service.
