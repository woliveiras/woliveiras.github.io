Adding labels sounds like a small change to the Task API. A caller can mark a task as urgent and retrieve it from the list. The moment you add `labels` to an existing response, that change reaches callers that never asked for labels. A worker that expects exactly `id` and `title` can stop reading tasks. The engineer who owns that worker has a question to answer before you decide how to release the feature.

## When to write an RFC

An **RFC**, or *request for comments*, is a written proposal that gives people a chance to review a change while the important choices are still open. It describes the problem, the proposed approach, the alternatives you considered, and the questions you need reviewers to help answer. The Rust project uses RFCs to discuss substantial changes to the language and its libraries. A team can use the same idea for a change to an internal API.

Write one when the decision needs input beyond the person implementing it. A response change affects consumer teams. A storage migration needs someone to check what happens on restart and recovery. For a validation fix where the expected response is already agreed, the [spec and tests](/books/hands-on-coding-assistants/chapters/the-spec-first-workflow/) can carry that decision into code review. In the labels exercise, the RFC gives the API and client owners room to discuss how the change reaches callers. A spec gives the implementation its observable behavior. An architecture decision record captures a design choice once it has been made.

## Write the proposal against the current system

Stay on `design-task-labels` with `notes/task-labels-epic.md` and `docs/architecture.md` committed from the previous exercises. Check the branch and your working tree, then open OpenCode from the lab root.

```sh
git branch --show-current
git status --short
opencode
```

Start a fresh session with `/new` if one is already open. Select **Plan** with `/agents`. Give it the proposal you want to explore and the files that describe the current system.

```text
Draft a request for comments on searchable labels for the Task API.
Read notes/task-labels-epic.md, docs/architecture.md, and src/app.ts.

Propose an in-memory release for the lab. Describe the problem, the
current API, the goal and scope, and the proposed update and filter
requests. Give each of these three alternatives its own heading:
1. Add labels to the existing response for all callers.
2. Offer an opt-in response version and keep the old shape available.
3. Keep the task response and expose labels as a separate resource.
For each, explain what a caller with a strict parser would have to do.
Include risks, adoption and rollback. Ask the client owner how we can
test compatibility and ask the operator when labels must survive a
restart. Keep the storage choice open. Return the draft in chat and
leave the files unchanged.
```

Check the draft against `GET /tasks`. The current service returns a list of tasks with `id` and `title`. In the proposal, `PATCH /tasks/:id/labels` replaces a task's labels, and `GET /tasks?label=urgent` filters the list. The additive option would include a `labels` array in both the list and task creation responses. Show what one task in the list looks like before and after that change.

```json
{"id":"1","title":"Write a spec"}
```

```json
{"id":"1","title":"Write a spec","labels":[]}
```

Those two objects give reviewers a specific compatibility question. Adding a field keeps the current keys available to callers that ignore extra fields. An opt-in version lets a caller choose when to adopt the new shape and gives the service two shapes to support. A separate labels resource preserves the original shape and adds requests for callers that need labels. Put those consequences beside each option so a reviewer can check the assumption about their own client.

If the draft groups always adding the field and letting callers opt in under the same option, ask Plan to split them. A strict client sees different payloads under those two choices. Keep the example payload and the compatibility question with whichever option you propose.

Give the draft an adoption condition and a way to reverse the change. For the lab, running the prior revision and checking `GET /tasks` can confirm that the original response shape is back. Starting that process resets the in-memory state, including tasks, labels, and registrations. State that effect in the rollback section.

Once you've reviewed the draft, switch to **Build** with `/agents` in the same session.

```text
Save the draft we just reviewed as docs/rfcs/0001-task-labels.md.
Mark it Draft and keep the open questions visible. Edit only that
document. Leave the working changes for me to review and commit.
```

Run `git status --short` and check that the RFC is the only changed file. Include the staged diff in your review so you can read the new document before committing it.

```sh
git add -- docs/rfcs/0001-task-labels.md
git diff --cached --check
git diff --cached -- docs/rfcs/0001-task-labels.md
git commit -m "Draft the task labels RFC"
```

## Keep the review attached to the draft

Share the draft with a teammate if one is available. Point them to the proposed response and rollout section and ask for an answer you can use. “Does the worker accept the candidate payload above? Which parser or test can we run to check?” gives the client owner a place to start. Ask the operator when they need labels to survive a restart and how they would check that behavior.

For the lab, you can use these two simulated review comments.

> **Client owner.** Our legacy worker rejects task objects with unknown fields. Its compatibility check needs to pass before we can change the response it receives.

> **Operator.** Labels need to survive a restart before production use. Please record who owns the storage decision and how we'll check recovery.

With the sample comments, try the client owner's objection against the two example task objects. This small stand-in for the worker expects exactly `id` and `title`.

```sh
node <<'JS'
const current = { id: "1", title: "Write a spec" };
const proposed = { ...current, labels: [] };
const accepts = (task) => Object.keys(task).sort().join(",") === "id,title";

console.log("Current response accepted", accepts(current));
console.log("Proposed response accepted", accepts(proposed));
JS
```

Expect `true` for the current object and `false` for the proposed one. You can use this result to explain the risk in the RFC. To make a rollout decision for a real caller, run its parser or compatibility suite against the candidate response.

Open a fresh **Plan** session so the reviewer works from the saved RFC and the comments you paste.

```text
Read docs/rfcs/0001-task-labels.md and review the comments below.
For each comment, identify the part of the RFC it affects and explain
what evidence supports it. Suggest a revision or a follow-up. Flag any
decision that needs the client owner or operator. Return your findings
in chat and leave the RFC unchanged.

Comments and evidence:
<paste the comments and the result of the compatibility check>
```

## Incorporate the feedback

Decide what changes in the proposal before asking Build to edit it. In this exercise, the client owner's feedback changes the adoption section. The additive response is suitable for the lab's intended callers. Keep the legacy worker on the existing response until its compatibility check passes or the team agrees on a different response strategy. The operator's feedback sets a production condition. Leave the lab release in memory and assign the storage decision to the service owner. The follow-up needs restart and restore checks before production use.

In a **Review and disposition** section, record what you heard, your response, and the place where the reader can see its effect. For the sample comments, two entries might look like this.

| Comment | Disposition | Where it goes |
| --- | --- | --- |
| The worker rejects extra fields. | Incorporated. Legacy rollout depends on its compatibility check. | Adoption section, with the client owner responsible for the check. |
| Labels need to survive restart. | Deferred to the durable release. | Follow-up for the service owner, with restart and restore as acceptance checks. |

If a comment is deferred or declined, give a reason the reviewer can respond to. Keep open questions visible when you still need evidence.

Switch to **Build** in the review session. Apply the changes one section at a time so you can check what the feedback changed. Use your own decisions if you worked with a different set of comments.

```text
Read the current docs/rfcs/0001-task-labels.md and revise only its
Alternatives and Adoption sections. Keep the three response
strategies separate. The lab uses the additive response for
clients that accept it. Legacy callers keep the existing shape
until their compatibility check passes or the team chooses a
different response strategy.
```

Read the diff to check that the adoption condition is in the proposal itself. Then apply the second change.

```text
In docs/rfcs/0001-task-labels.md, update only Rollback and Review
and disposition. In Rollback, explain how to run the preceding
revision and check the original GET /tasks response. State that
restarting resets in-memory tasks, labels, and registrations.
In Review and disposition, record both original comments and
their dispositions. Assign the durable follow-up to the service
owner with separate restart and restore checks before production.
```

Read the diff alongside the draft commit. Check that a reader can find each comment and what happened to it. If an edit failed or a row is missing, give Build the current section and the exact reviewed text to apply. Check the rollback command and make sure someone can pick up the durability follow-up from the review record. If you used a real reviewer, send them the revised section and ask them to confirm it addresses the concern they raised.

```sh
git diff -- docs/rfcs/0001-task-labels.md
git add -- docs/rfcs/0001-task-labels.md
git diff --cached --check
git commit -m "Address task labels RFC review"
```

The next chapter uses the revised RFC to [record the architecture decision](/books/hands-on-coding-assistants/chapters/record-the-architecture-decision/) for the durable follow-up. Keep the review record in the RFC so the next reader can see where the restart requirement came from.
