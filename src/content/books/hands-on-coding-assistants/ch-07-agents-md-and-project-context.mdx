## Give the next session a reliable start

An assistant can see the route in the lab and still guess the test command. This is what `AGENTS.md` is for. Write the facts a new contributor needs before working on a task. Leave one-off decisions in the feature spec.

The starter already has a root `AGENTS.md`. Compare it with `package.json` and `src/app.ts`. The file names the test command, explains where routing lives, and tells the agent to treat `contracts/` as acceptance criteria. Each instruction has a consequence you can observe in a session.

## Keep instructions close to the work

OpenCode reads project guidance from `AGENTS.md`. It can discover nested files during work in their directories. Start with the root. Add narrower guidance when a directory has a real difference, such as a contract suite with different rules for modifying tests. OpenCode combines instruction sources, so check for contradictory rules before adding another file.

A line like “follow our testing conventions” requires the assistant to infer those conventions. “Use the helpers in `test/client.ts` so each test gets a fresh server” gives it a file, a behavior, and a reason. Check that the instruction still makes sense when you read it six months later.

## Test what the assistant learned

1. Start a fresh Plan session in the lab.
2. Ask where you'd add a test for a blank task title and which command you'd run.
3. Check whether it points to `test/app.test.ts`, uses the HTTP helper in `test/client.ts`, and identifies `npm test`.
4. Ask how the registration contract differs from the starter suite. It should find `npm run test:registration` as the opt-in command.

If the assistant misses the distinction, open the files yourself and improve one instruction. Repeat with a new session and the same model. That controls for context left over from the first run.

## Keep guidance and enforcement visible

“Leave the acceptance tests unchanged” is a useful rule for the agent and for a human reviewer. Check the diff to enforce it for this task. When the rule is a repository invariant, you can also enforce it with a test, a review requirement, or a tool permission. Match the enforcement to the consequence of breaking the rule.
