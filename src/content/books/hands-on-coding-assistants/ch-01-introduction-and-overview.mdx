## What this book covers

If an assistant says it fixed an endpoint, you still need to know which files changed, whether invalid input reaches storage, and which tests it ran. A confident summary leaves all three questions open.

Those questions are the reason for this book. You'll give an assistant a bounded task, watch how it works, and decide whether the resulting change belongs in the codebase. The model is interchangeable. The spec, the tests, and the diff are what you carry from one tool to another.

## Model, harness, and workspace

| Layer | In this book | What you can inspect |
| --- | --- | --- |
| Model | A locally served or free hosted model | The selected model, its output, and whether it calls tools correctly |
| Harness | OpenCode in the terminal | Files it reads, edits it proposes, commands it runs, and permission prompts |
| Workspace | The Task API lab and your Git branch | The source, instructions, tests, and final diff |

A model proposes the next action. The harness supplies tools and can execute a permitted action. OpenCode's Build and Plan agents have different default permissions, which matters when a request moves from exploration to implementation.

The difference becomes visible once you change models. One model might read the right file and run the tests. Another might describe the test it wants to run and stop. Open the session's tool activity and compare both outcomes with the command you run yourself.

## Start with a result you can check

Run `npm test` in the lab to establish the baseline. After [setting up OpenCode](/books/hands-on-coding-assistants/chapters/setup-and-practical-integration/), use that baseline to [check what the agent tells you about the code](/books/hands-on-coding-assistants/chapters/exploring-an-unfamiliar-codebase/). Give it a question about one request and compare its answer with the handler and the test.

## When the work gets harder

A fluent explanation can hide a missing tool call, an out-of-date assumption, or a test that checks the wrong behavior. Read the relevant code yourself before reviewing a change in an unfamiliar area. An experiment with experienced open-source developers also illustrates why it pays to measure review and correction time. In that study, participants took longer in the AI-enabled condition even though they expected a speedup. That result describes the study's tasks and setting.

In [The Spec-First Workflow](/books/hands-on-coding-assistants/chapters/the-spec-first-workflow/), you'll give two models the same implementation task and check them against the same acceptance tests. Your first comparison can be as simple as whether the change passed and how many times you had to intervene.
