## The recurring problem

Two sessions can start with the same prompt and end up changing different files. One reads the test and follows the route. The other assumes the project uses a framework it has seen before. The fix starts with the context and checks both sessions should have.

A harness is what connects a model to the workspace and gives it tools. In the lab, OpenCode handles that connection. You shape its behavior with the files you version, the commands you permit, and the decisions you keep for yourself.

## The three layers

| Layer | In the Task API | Add to it when |
| --- | --- | --- |
| Project context | `AGENTS.md`, `specs/`, and the code | The model keeps inferring a convention you can state once |
| Tool selection and permissions | OpenCode, its agents, and `opencode.jsonc` | A task needs a distinct role or a different set of permissions |
| Verification | `npm test`, feature contracts, and `git diff` | An important requirement has no observable check |

The registration spec belongs to the task. The rule about leaving acceptance tests in place belongs to the repo. The shell approval belongs to the harness. When you put a rule in the wrong layer, it can look present while failing to affect the outcome. A line asking the assistant to avoid editing files can guide it. A denied edit permission is checked by the harness.

## Follow one request through the harness

Take the registration exercise and write down the path it follows:

1. You select **Plan** and point it to the spec and the current route.
2. The model requests a file read. OpenCode supplies the tool and returns the result.
3. You review the plan and select **Build**. OpenCode can now apply edits under that agent's permissions.
4. The model asks to run a test command. OpenCode checks the command against the project rules.
5. You run the checks yourself and read the diff.

The point where work fails tells you what to change. If a model lacks a project convention, fix the instruction. If it proposes the right behavior and submits a wrong patch, bring it back to the failing assertion. If a correct patch cannot be verified from a fresh checkout, fix the test setup.

## Add one layer at a time

Start with the lab's root instructions and one contract. Reuse those for a few changes before adding a separate reviewer, a skill, or a tool server. That gives you a baseline. When you add a component, check whether a session now finds the right context sooner or needs fewer corrections.

For a larger harness, I wrote about how Geremmyas keeps specs, checks, and review records around the tools a developer already uses. The Task API gives you the same decision at a smaller scale. Decide what needs to persist between sessions, and put that information in a file that the next session can read.
