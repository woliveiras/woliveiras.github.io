The registration handler returned `400` for an invalid request, just as the spec said. The next valid request exposed the bug when it got ID `"2"` on a fresh server. You had to look at two requests to see that the first one changed state. In the outage exercise, you had a similar problem at a different scale. One trace explained what happened to a request. Counting responses told you how often callers ran into it.

A **harness** is the setup around a coding agent that gives it project context, limits what it can do, and checks the results of its work. OpenCode already provides the agent, tools, and a way to configure permissions. Your repository adds the parts that know about your project. The spec says what the code must do. `AGENTS.md` can tell the agent which command to run. The test runner executes the assertions and gives you an exit status. A required CI check can make that result a condition of merging. An alert can show you when a deployed service is failing and give the responder somewhere to start.

In this exercise, you'll use the bug and the postmortem to decide what to check, prove that a test can reject a broken version, and record what a later alert will have to demonstrate.

## Bring the earlier evidence into OpenCode

Use the root of your lab fork. Start on `incident-postmortem` with a clean working tree and the committed `notes/postmortem.md`. You'll also need the registration fix note committed on `debug-registration`, or whichever branch you used in the debugging chapter.

```sh
git branch --show-current
git status --short
opencode
```

Open a fresh session with `/new` and choose **Plan** with `/agents`.

```text
Read notes/postmortem.md. The earlier registration fix is on
debug-registration, in notes/registration-fix.md. Tell me how to
read that committed note from this checkout without switching
branches. Wait for me to paste it before suggesting controls.
```

Check the branch and path the agent gives you. The following command prints the note from the earlier commit. Substitute your branch name if you used a different one.

```sh
git show debug-registration:notes/registration-fix.md
```

Paste the note into the same session. You now have two records with a different job. The fix note shows a behavior you can reproduce on demand. The postmortem shows a symptom you want to detect while the service is running.

## Put the check where it can see the failure

```text
Use the fix note I pasted and notes/postmortem.md. Propose one control
for each confirmed failure. Cite the observation it should catch.
Name where it runs, what healthy and failing cases look like, what
output I should keep, and who acts on a failure. If a control needs
another step to enforce it, name that step. Leave files unchanged.
```

Review the proposals against the original evidence. A check that asserts only the `400` response would accept the broken registration handler. The test needs to send a valid request on the same server afterward and check that it gets ID `"1"`. In the postmortem, a slow span explained one timeout. To detect a service-wide problem, look at how many gateway requests fail within a window and how much traffic the gateway is serving.

Say where each control takes effect. The lab's OpenCode permissions allow `npm run test:registration`. The permission lets the agent run the command when it needs to. To make the result matter at merge time, require a CI job that actually runs the check. If the suggested control is a review, decide what the reviewer must be able to reproduce from the spec, diff, and test output.

## Choose one change to make repeatable

Start with registration. The behavior is already in the spec, the lab has a known defective version, and you can run the check without Docker. Carry the gateway error signal forward to the alert exercise. There you'll need live traffic and a receiver to verify delivery and recovery.

Ask **Plan** to turn the first choice into commands you can inspect before running.

```text
Plan a two-version check for registration. Compare lab-debugging and
lab-registration in temporary detached Git worktrees. Use the same
commands in both worktrees. Compare package.json,
contracts/registration.test.ts, and test/client.ts between the tags.
Give me commands I can run in a second terminal. Tell me which
assertion should fail on the defective version and what a passing
result on the corrected version should look like.
```

The contract already covers the sequence you need. Use two worktrees, which are separate checkouts of the same Git repository. Keep OpenCode in the original checkout for this exercise and run the commands in a second terminal from the fork root.

```sh
git worktree add --detach ../task-api-harness-bug lab-debugging
git worktree add --detach ../task-api-harness-fix lab-registration
git diff lab-debugging lab-registration -- package.json contracts/registration.test.ts test/client.ts
git rev-parse lab-debugging lab-registration
```

The diff should be empty. Record the two commit IDs in order. Record `node --version` too and use the same Node installation for all three runs. The lab needs Node 24 or later.

## Verify the check on both versions

First run the base suite in the defective checkout.

```sh
(cd ../task-api-harness-bug && npm test)
```

Expect three passing tests. The base suite covers the task API. Its result gives you a useful comparison with the registration contract. Run the contract on each checkout separately and read the exit status immediately after each run.

```sh
(cd ../task-api-harness-bug && npm run test:registration)
echo "$?"
```

Expect exit `1`. The invalid requests get `400`, and the next valid request returns ID `"15"` where the test expects `"1"`. The contract sends fourteen invalid requests, so it exposes the same allocation bug you saw with one invalid request. Read the failed assertion. A missing test file or an unsupported Node version would leave this verification incomplete.

```sh
(cd ../task-api-harness-fix && npm run test:registration)
echo "$?"
```

Expect two passing tests and exit `0`. Paste the outputs and revisions into the original **Plan** session.

```text
I pasted the command output and revisions from both worktrees. Tell
me what each result proves. Quote the failing assertion and explain
why the base suite stayed green. Flag anything that would prevent
me from using this as evidence for a required CI check later.
```

Check that the agent attributes the results to the right revisions. You can now show that the contract distinguishes the two versions. Later, the merge exercise will check whether GitHub actually requires the result for the change being reviewed.

## Check the alert signal against the outage

Still in **Plan**, use the postmortem to verify that your proposed signal would have distinguished the affected period from recovery.

```text
Read the Prometheus evidence in notes/postmortem.md. Compare the
timeout count and total request count in the affected window with
the first clean bucket. Use that comparison to propose a gateway
error signal. Give me the healthy, degraded, and recovered cases
I should exercise to verify a future alert and its notification.
Keep alert delivery and the live threshold open until we test them.
```

Check the arithmetic against the note. The replay had `60/300` timeouts in the affected three minutes and `0/100` in the first clean minute. The counts tell you that traffic continued while the errors went away. If an interval has no requests, that interval gives you no evidence that callers can create tasks successfully.

Keep the ratio of gateway `5xx` responses to total requests as the signal to try. It includes the `504`s from the outage and leaves expected validation responses such as `400` out of the error count. You'll exercise a rule on live gateway counters, then check that degraded traffic produces a firing notification and healthy traffic produces a resolved one. The responder should be able to use the alert to reach the relevant dashboard and traces.

## Record the controls and their evidence

Switch to **Build** in the same session. Ask it to save your decision and the results you checked.

```text
Write notes/harness.md using the results and decisions we reviewed.
For each selected control, record the failure, where the control
runs, who acts on it, and the evidence needed to accept it. For the
two-version proof, record npm run test:registration and
contracts/registration.test.ts, both revisions, the Node version,
and the observed assertion and exit statuses. Keep the earlier
focused regression in the fix note. For the alert, record 60/300
during the incident and 0/100 in the first clean bucket. Mark CI
enforcement, the live threshold, and alert delivery as pending.
Write only notes/harness.md.
```

Open a fresh **Plan** session to review the saved record.

```text
Read notes/harness.md and notes/postmortem.md. Check that I could
repeat the two-version registration test from the note. Check what
the replay actually proves about the alert and what still needs a
live test. Give me findings with file and section references.
```

Check any findings against the outputs you kept. The two-version proof should cite the same contract file on both tags. Its failing assertion is `"15"` versus `"1"`. If the note uses the focused test's `"2"` result or claims the threshold and delivery were verified, give **Build** the relevant output and have it correct the note. Inspect the staged note, commit it, then remove the two temporary checkouts.

```sh
git status --short --untracked-files=all
git add -- notes/harness.md
git diff --cached --check
git diff --cached -- notes/harness.md
git commit -m "Record the first harness controls"
git worktree remove ../task-api-harness-bug
git worktree remove ../task-api-harness-fix
```

Keep the note on `incident-postmortem`. Start [Focused Tests and Coverage Gates](/books/hands-on-coding-assistants/chapters/test-generation-and-improvement/) from the known-good `lab-registration` checkpoint. You'll add focused tests, verify that they catch a regression, and give coverage a threshold the runner can enforce. [Required CI Checks and Merge](/books/hands-on-coding-assistants/chapters/required-ci-checks-and-merge/) takes that verification to a clean checkout. Bring your alert cases to [Instrument the Service and Verify the Alert](/books/hands-on-coding-assistants/chapters/instrument-the-service-and-verify-the-alert/).
