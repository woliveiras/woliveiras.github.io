The Task API's tests tell you how the service handles an invalid request. If that convention lives in a tool outside the repository, the agent needs a client that can discover the tool and call it. **Model Context Protocol**, or **MCP**, defines that exchange. OpenCode is the client here. It starts the local server, negotiates the protocol, discovers the tool and its input schema, and can send the tool's result to the model.

Use a new exercise branch at `lab-start`. The included server, `tools/project-context.mjs`, uses standard input and output. It provides a fixed response about task validation and needs no network service or credential.

```sh
git switch -c context-tool lab-start
npm run test:mcp
```

Expect one passing test. It starts the process, sends initialization and tool requests, and checks their replies. This gives you a process-level check before involving OpenCode.

## Connect the server in OpenCode

Open **Plan** and ask how to interpret the smoke test before you configure the client.

```text
Read tools/project-context.mjs and contracts/mcp.test.ts.
Trace initialization, tool discovery, and the conventions
reply. Tell me how to configure OpenCode to start this process
and what I should inspect to verify a real tool call.
```

Read the server yourself. Check which executable and path OpenCode will use. Merge the following top-level block into `opencode.jsonc`, keeping the existing permissions. With `codemode: false`, this server's tool is presented directly, which makes the call easier to identify in the exercise.

```jsonc
{
  "mcp": {
    "servers": {
      "project_context": {
        "type": "local",
        "command": ["node", "tools/project-context.mjs"],
        "codemode": false
      }
    }
  }
}
```

From the fork root, run the client discovery check.

```sh
opencode mcp list
```

Look for `project_context` with a connected status. If OpenCode `2.3.2` reports no servers on its first request, check the working directory, config, and smoke test. Retry in the same normal background service after it has had time to discover the server. That version has a cold registry issue. A working standalone smoke test narrows the diagnosis to the client setup when OpenCode fails to connect.

## Ask the model to call it

Open OpenCode from the same location and use a fresh **Plan** session.

```text
Call project_context_get_task_conventions with an empty argument
object. If that tool is unavailable or denied, report it and stop.
Use only the named MCP tool to obtain the result. Quote its observed
response and identify a test in test/app.test.ts that checks the same
behavior.
```

Look for a completed call to the named tool. The response says invalid task input returns HTTP `400` and leaves stored tasks unchanged. Open the blank-title test and find its assertion on the task list after the rejection. The matching test supports the convention. The tool event shows where the session actually got it.

Now append a narrow denial to the project's `permissions` array.

```jsonc
{ "action": "project_context_get_task_conventions", "resource": "*", "effect": "deny" }
```

Reopen OpenCode with the changed config and try the same prompt in a new session. Discovery can still list a connected server while the tool is unavailable or denied. Check the tool activity. If the agent suggests calling the server through the shell, stop at that point and keep the probe scoped to the MCP tool. Restore the permission and confirm that a fresh session can call the tool again.

Save what you observed at process startup, discovery, and invocation. Commit the working configuration on `context-tool` after checking that you removed the temporary denial.

```sh
git diff -- opencode.jsonc
git add -- opencode.jsonc
git diff --cached --check
git commit -m "Connect the Task API MCP example"
```

For a service you connect later, review the commands and credentials it needs and document what each exposed tool can do. In [AI-First Security & Governance](/books/hands-on-coding-assistants/chapters/ai-first-security-and-governance/), you'll apply the same check to the boundaries of a review.
