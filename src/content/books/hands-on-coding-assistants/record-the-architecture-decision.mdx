The [reviewed RFC](/books/hands-on-coding-assistants/chapters/write-and-review-an-rfc/) keeps the first labels release in memory. In the sample review, the operator asks for labels to survive a restart before production use. The next decision is where tasks and their labels should live and how the operator should recover them.

## When to write an ADR

An **architecture decision record**, or **ADR**, records an architectural choice and the reasons for it. A maintainer should be able to read it later and see which constraints mattered, what other options were plausible, and what would make the team revisit the decision.

Write an ADR when a choice has lasting effects on how you build, operate, or change the system. Choosing a store affects deployment, upgrades, and recovery. The labels RFC preserves the discussion that exposed those concerns. The ADR records the storage decision that follows from it. The implementation spec still defines what callers can observe, such as what a request to clear labels returns.

## Start from what the discussion settled

Stay on `design-task-labels` with the revised `docs/rfcs/0001-task-labels.md` committed. Read its **Review and disposition** section. Find the storage follow-up and the checks that came out of the review. The sample review calls for restart and restore checks. Open `docs/architecture.md` to see how the current process owns its in-memory state. Keep `specs/task-labels.md` at hand for the first release's API behavior. Those expectations carry into the final project.

For the durable follow-up, assume one host, one Task API instance responsible for writes, and a persistent local disk. The operator needs to back up and restore the data. Treat several writable instances on different hosts as a reason to revisit the decision. These exercise assumptions give you a way to compare the options.

```sh
git branch --show-current
git status --short
opencode
```

Check that you're on your design branch with a clean working tree. Start a fresh OpenCode session with `/new` if one is already open, then use `/agents` to select **Plan**.

```text
Read docs/rfcs/0001-task-labels.md, docs/architecture.md, and src/app.ts.
Find the storage follow-up in the RFC review and explain what happens
to task state in the current service after a restart.

For the follow-up, assume one host, one writable Task API instance,
and a persistent local disk. Tasks and labels must survive restart.
The operator needs a way to back up and restore the data. Compare
in-memory storage, SQLite, and a shared PostgreSQL service against
those constraints. Give the operational cost of each option and say
what would make us revisit the choice. Return the comparison in chat
and leave the files unchanged.
```

Read the comparison alongside the RFC. The in-memory arrays are easy to run and lose their contents on restart. A SQLite file on persistent storage can fit a single-host deployment. It gives the operator a local database to manage, with schema migrations, file permissions, and backups to verify. A shared PostgreSQL service gives application instances on different hosts a common place to write. It adds a database service to provision and operate. A **decision driver** is a requirement or constraint that changes how those trade-offs matter. Here, restart survival rules out keeping the arrays as the only store for the follow-up. The local disk and single writable instance make SQLite a reasonable choice for this exercise.

## Write the record and choose its status

**Markdown Architectural Decision Records (MADR)** is a Markdown template for writing ADRs. This exercise uses version **4.0.0**. The context states the problem, the options show what you considered, and the outcome records the decision and its reasoning. Three optional sections are useful here. **Decision Drivers** explains what constrains the storage choice. **Consequences** captures the work and trade-offs you accept. **Confirmation** describes how you will check that the implementation follows the decision.

MADR also provides optional YAML metadata. Use `status` to record where the decision stands, `date` for when it was last updated, and `decision-makers` when it helps to name who made the choice. A `proposed` record is still up for review. An `accepted` record captures agreement on the choice. The confirmation checks may still be ahead of you.

Review the options and choose one before asking for the draft. If you choose SQLite under the exercise assumptions, use this prompt in the same Plan session and paste the example that follows it. Adapt the choice and reasoning if your assumptions differ.

```text
Draft the durable follow-up using the Markdown Architectural Decision
Records 4.0.0 example I pasted. Keep its headings and YAML frontmatter.
The choice for this exercise is SQLite on persistent local storage for
one host and one writable Task API instance. Explain why the choice
fits, what migration and backup work it adds, and when to reconsider
it. Under Confirmation, describe future restart and restore checks
with expected results. Link the reviewed RFC and the in-memory labels
spec. Keep status proposed and return the draft in chat.
```

Compare the draft with this example. The outcome says why SQLite fits, and each confirmation check would catch a different way of losing the data.

```markdown
---
status: proposed
date: "YYYY-MM-DD"
---

# Store durable task labels in SQLite

## Context and Problem Statement

The labels RFC keeps the lab release in memory. The durable follow-up
needs to preserve tasks and labels after a restart and recover them
from a backup.

## Decision Drivers

- The service runs on one host with one writable Task API instance.
- Tasks and labels survive a process restart.
- The operator can back up and restore the database.

## Considered Options

- In-memory arrays. The existing process can serve requests, and a
  restart clears the arrays.
- Local SQLite. The application owns a database file on persistent
  storage. The operator needs a backup and restore procedure.
- Shared PostgreSQL. Application instances can use one database from
  different hosts. A separate service needs to be operated.

## Decision Outcome

Use SQLite for the durable follow-up. A local database on persistent
storage fits the single-host deployment and gives the operator data
they can back up and restore. Revisit the choice if instances on
several hosts need to write to the same store.

### Consequences

The follow-up needs schema migrations, a persistent file location, and
permissions for the application and backup process. The labels exercise
continues to use the in-memory API described in its spec.

### Confirmation

After implementation, create a task and attach the label urgent.
Once the update succeeds, restart the service with the same database
file. Filtering by urgent must return the same task ID, title, and labels.

Create a consistent backup using SQLite's supported backup mechanism.
Restore it into an isolated database and start a separate instance
against the restored copy. Repeat the query and check the same ID,
title, and labels.

## More Information

- [Task labels RFC](../rfcs/0001-task-labels.md)
- [In-memory labels spec](../../specs/task-labels.md)
```

Review the draft against the RFC. If it says SQLite is already running in the lab, ask Plan to trace the storage code in `src/app.ts` and revise the context. Check that the tests under **Confirmation** describe what a future implementation must demonstrate. A newly created task lets you verify that recovery preserved your data even when the service also has seeded tasks.

## Keep the three records linked

Once you've chosen an option and can explain its consequences, you can mark the ADR `accepted` for this exercise. On a team, keep it `proposed` while the decision is still open. Replace the sample date with the date you're updating the record. Switch to **Build** with `/agents` in the same session and fill in the two placeholders before sending the prompt.

```text
Save the reviewed MADR draft as docs/decisions/0001-task-label-storage.md.
Start the file with a YAML block delimited by --- lines. Set status
to <proposed or accepted> and date to <YYYY-MM-DD>. Preserve the
approved choice and the future confirmation checks. Under More
Information, link ../rfcs/0001-task-labels.md and ../../specs/task-labels.md.
Write only the ADR and leave the changes for me to review and commit.
```

Run `git status --short --untracked-files=all`. You should see only the new ADR. Open it and check that the status and date are between the two `---` lines at the top. Open both links from the saved file. Then stage the document and read the full diff before you commit it.

```sh
git add -- docs/decisions/0001-task-label-storage.md
git diff --cached --check
git diff --cached -- docs/decisions/0001-task-label-storage.md
git commit -m "Record the durable task labels storage decision"
```

When you reach the [final project](/books/hands-on-coding-assistants/chapters/end-to-end-final-project/), the RFC will explain the rollout discussion, the ADR will explain the durable follow-up, and the spec will give you the behavior to implement in memory. If the storage choice changes later, write a new ADR and mark the previous one as superseded with a link to its replacement.
