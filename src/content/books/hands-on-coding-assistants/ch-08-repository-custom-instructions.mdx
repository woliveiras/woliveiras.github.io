The nested guide in [AGENTS.md & Project Context](/books/hands-on-coding-assistants/chapters/agents-md-and-project-context/) became available when the reviewer entered a directory. A project can also load an existing guide by path. Then you can use one command to ask the same review question for different specs. The guide describes the report, the command supplies the prompt, and a permission rule controls whether a tool can edit a contract.

Start at `lab-start` so you can observe the new guide on its own. Create the directories for the guide and command.

```sh
git switch -c custom-instructions lab-start
mkdir -p docs .opencode/commands
```

Save the following review guide. Its label gives you something specific to check when you run the command.

```md title="docs/review-guide.md"
In a contract review, include a row labelled "State after rejection".
Name the assertion that observes it, or mark that row as unchecked.
```

Add `"instructions": ["docs/review-guide.md"]` as a top-level entry in `opencode.jsonc`, keeping the existing entries. The configured guide joins the initial guidance after the discovered `AGENTS.md` sources. If two files give different instructions for the same decision, reconcile them where they are written.

## Add a command that starts from a spec

Save this template as `.opencode/commands/check-spec.md`. OpenCode substitutes the text you supply for `$ARGUMENTS` and runs the prompt with **Plan**.

```md title=".opencode/commands/check-spec.md"
---
description: Match a Task API spec to its contract checks
agent: plan
---

Read the spec at $ARGUMENTS and the related acceptance test.
Return a row for each criterion with a check and expected result.
Flag any criterion without a check. Leave files unchanged.
```

Reopen OpenCode from the fork root, start a fresh session, and run the command.

```text
/check-spec specs/registration-validation.md
```

Check the tool reads for the spec and `contracts/registration.test.ts`. Look for **State after rejection** and confirm that it names the successful response with ID `"1"` after the invalid requests. The contract includes an overlong name of 101 characters. If the report says it tests exactly 100, open the input list and ask Plan to mark that case as unchecked. If the label is missing, check the path in `instructions`, then rerun in a fresh session to verify that the guide is present.

## Keep permissions in the config

A command can tell an agent to leave a file alone. To block an edit through OpenCode's edit tools, append this rule to the existing project `permissions` array. OpenCode applies the last matching rule. An agent-specific rule can also affect the final result.

```jsonc
{ "action": "edit", "resource": "contracts/*", "effect": "deny" }
```

Reopen OpenCode, start a fresh **Build** session, and run a controlled probe.

```text
Use the edit tool on contracts/registration.test.ts. Replace its
first line, import assert from "node:assert/strict";, with two lines.
The first is // Permission exercise and the second is the original
import. Report the result of this single edit attempt in chat.
```

Look for the denied action in the tool activity, then verify the contract file remains unchanged.

```sh
git diff --exit-code -- contracts/
git status --short --untracked-files=all
```

A refusal in chat shows the agent's response. Look for an actual denied edit before recording the rule as verified. If the tool reports a no-op, check the proposed replacement and repeat with a change to the text. If an edit succeeds, check the selected agent, rule order, and configuration path before repeating the probe.

Review the guide, command, and config diff. Commit those files on `custom-instructions` and keep the observed command result with your exercise notes.

```sh
git add -- docs/review-guide.md .opencode/commands/check-spec.md opencode.jsonc
git diff --cached --check
git commit -m "Add a scoped contract review command"
```

In [Agent Skills & Modular Expertise](/books/hands-on-coding-assistants/chapters/agent-skills-and-modular-expertise/), you'll give the agent a procedure it can load when a task calls for it.
