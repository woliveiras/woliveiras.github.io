## What belongs where

Once you have both a root `AGENTS.md` and `opencode.jsonc`, decide which layer owns each new rule. The distinction pays off when a second person opens the repo, or when the same instructions are used with a different harness.

| Need | Where it belongs in the lab |
| --- | --- |
| Explain why an invalid request leaves state unchanged | `AGENTS.md` |
| Describe this feature's exact payload and response | `specs/task-labels.md` |
| Carry a review prompt you run on demand | `.opencode/commands/` |
| Control which shell commands an agent may run | `opencode.jsonc` |

OpenCode also accepts an `instructions` array in its config. Use it when an existing repository document already holds the rules you need. Point to that document and keep its instructions in one place. OpenCode adds those sources alongside discovered `AGENTS.md` files.

## Add a command that starts from a spec

Create `.opencode/commands/check-spec.md`. The file becomes the `/check-spec` prompt in OpenCode. The template substitutes the argument you pass.

```md title=".opencode/commands/check-spec.md"
Read the spec at $ARGUMENTS and the related acceptance test.
Return a table with one row per criterion. For each row, name a
check and the expected result. Flag criteria with no check.
Leave files unchanged.
```

Select **Plan**, then run:

```text
/check-spec specs/registration-validation.md
```

Compare the result with `contracts/registration.test.ts`. A good answer identifies the valid request, the failing input classes, and the ID check. It also notices if a spec criterion lacks a test. You can verify the result without asking the assistant to change the test suite.

## Keep permissions in the config

Read the starter's `opencode.jsonc`. The broad shell rule asks for approval. The rules below it allow the specific test commands. OpenCode evaluates matching rules in order, with the last matching rule winning in that sequence. Geography matters too. The starter denies access outside the project boundary through the dedicated directory action.

When a reader follows the command in **Build**, “leave files unchanged” is part of the prompt. For a session that must enforce read-only behavior, select **Plan** or use the reviewer definition from [Custom Agents & Sub-Agents](/books/hands-on-coding-assistants/chapters/custom-agents-and-sub-agents/). Keep that choice visible when you document the workflow.
