## Start with the behavior

The starter already tests a blank title. It doesn't test the upper bound for a task title. Before asking the assistant for coverage, decide what the caller should see. A title with 120 characters is valid. One with 121 returns a 400 and leaves the stored list unchanged.

Ask **Plan** to read `src/app.ts` and `test/app.test.ts`. Have it identify the existing cases and propose checks for both sides of the boundary. Then ask **Build** to add those tests in `test/app.test.ts`. Keep the application and the contract files out of this change.

## Read the assertions

A test that checks only for HTTP 400 leaves an important question unanswered. The server could store the task and still return an error. Check the state through the API.

```typescript title="test/app.test.ts"
test("a title over the limit leaves tasks unchanged", async t => {
  const request = await startApp(t);
  const before = await (await request("/tasks")).json();
  const response = await request("/tasks", jsonRequest("POST", {
    title: "x".repeat(121),
  }));
  assert.equal(response.status, 400);
  assert.deepEqual(await response.json(), { error: "invalid_task" });
  assert.deepEqual(await (await request("/tasks")).json(), before);
});
```

Ask for a separate success case at exactly 120 characters. The two cases catch both directions of an off-by-one mistake. Use the real HTTP helper. Mocking the validation function would skip the response mapping and the state change, which are the behaviors you want to know about.

## Check that a new test catches a regression

Run `npm test`. If the new tests pass, try them against a temporary local change from `title.length > 120` to `title.length >= 120`. The exact-limit case should fail. Undo only that deliberate change and run the suite again. Start with a clean branch or save your own edits before trying this, so you can see exactly what you have restored.

For a failure in the registration exercise, use `npm run test:registration` alongside the starter suite. That contract is supplied with the book. The tests you're writing here cover a different route and belong in the regular suite.

## Decide what layer to test

A pure label-normalization helper is cheap to cover with a unit test if you extract one in the final project. An HTTP test is more useful for status, payload, and persistence within one request sequence. The lab's built-in Node.js test runner supports both. Pick the layer where a failure answers the question you have.
