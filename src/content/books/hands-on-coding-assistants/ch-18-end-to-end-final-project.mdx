## The scenario

A user of your task API wants to mark a task as urgent and find it again from the list. You have task creation and listing. The new feature needs a way to replace a task's labels, clear them, and filter the list by one label.

Start from the lab's original commit on a fresh branch. If you kept the registration work, keep that branch available for comparison. The labels exercise stands on its own.

```sh
npm test
npm run test:labels
```

The starter tests pass and the labels contract fails. Open `specs/task-labels.md` and compare its expected behavior with `contracts/labels.test.ts` before opening an agent.

## Plan the change

Select **Plan** and ask the agent to read the spec, contract, and `src/app.ts`. Look for a plan that answers these questions:

- How do new and existing tasks get an empty labels array?
- Where does validation finish before assigning labels to a task?
- How does filtering apply the same normalization as storing a label?
- Which existing tests need an updated response shape while keeping their behavior checks?

Pay particular attention to the distinction between invalid input and a valid empty array. The first must preserve the stored labels. The second means clear them. Also check the order of normalization and deduplication. A stored list containing both `Urgent` and `urgent` would change what readers see even if the filter still returned the right task.

## Implement in small steps

Switch to **Build**. Ask for the data shape and response changes first. Then add the update route and filtering. If the model tries to change the acceptance contract, bring it back to the constraint in the spec.

Run the checks yourself:

```sh
npm test
npm run test:labels
git diff --check
git diff -- src/app.ts test/app.test.ts
```

The existing test assertions should still cover title normalization and invalid title behavior. Their expected response objects now include `labels`. The separate acceptance suite checks case normalization, duplicates, clearing, filtering, an unknown task, and preservation of state after invalid input.

## Review the feature like a maintainer

Use the reviewer from [Custom Agents & Sub-Agents](/books/hands-on-coding-assistants/chapters/custom-agents-and-sub-agents/) or start a fresh Plan session. Ask it to focus on backwards compatibility of `id` and `title`, state after rejection, and filter behavior. For each finding, ask for a concrete request you can reproduce. Apply a correction only after you can explain the failure.

Try the route yourself in the running lab:

```sh
curl -i -X PATCH http://127.0.0.1:3000/tasks/1/labels \
  -H 'Content-Type: application/json' \
  -d '{"labels":[" Urgent ","bug","urgent"]}'
curl -i 'http://127.0.0.1:3000/tasks?label=urgent'
```

Run `npm start` in a separate terminal before these requests. The update should return 200 with `["urgent","bug"]` in the task's `labels` array. The list should contain that task. Stop the server when you're finished.

## Leave a record someone else can use

Write a short change summary with the agreed behavior, the files you changed, your verification commands and results, and any follow-up deliberately left out. If you compared models, record where each needed help. Keep the final diff and tests with the spec. They give the next reviewer a starting point even when the assistant's session is gone.
