## The scenario

A user wants to label a task as urgent and find it again. You've done the design work for a larger feature. Now ship a small version that stores labels in memory. The RFC and ADR explain the future durable version. The exercise's label spec defines what a caller should see from the version you implement.

Bring your [reviewed RFC](/books/hands-on-coding-assistants/chapters/write-and-review-an-rfc/#incorporate-the-feedback), [storage ADR](/books/hands-on-coding-assistants/chapters/record-the-architecture-decision/), and [harness note](/books/hands-on-coding-assistants/chapters/building-your-harness/#record-the-controls-and-their-evidence). Substitute the branch names you used.

```sh
git show design-task-labels:docs/rfcs/0001-task-labels.md
git show design-task-labels:docs/decisions/0001-task-label-storage.md
git show incident-postmortem:notes/harness.md
git show ci-evidence:notes/ci.md
git show instrument-alerts:notes/alert-verification.md
```

Keep the design constraints for Plan. Use the CI and alert notes to check where you verified the branch rule and how you found a gateway log and its trace.

Start from a clean checkout of your fork with Node `24.22.3`. The base branch supplies the verification workflow, coverage policy, and live gateway. Keep it at this commit while you review and run CI.

```sh
git switch -c capstone-base lab-harness
git switch -c task-labels
npm run verify
npm run test:labels
```

Expect ordinary verification to pass and both label contract tests to fail before implementation. Keep both results for the PR. The starter's verification uses the tests selected by the harness, and this feature's contract still needs to be included in the ordinary run.

## Plan the change

Open OpenCode from the fork root. In **Plan**, give it the relevant decisions from the RFC and ADR and ask it to read the actual acceptance criteria.

```text
Read specs/task-labels.md, contracts/labels.test.ts, src/app.ts,
and test/app.test.ts. Use the design decisions I pasted to plan
the in-memory labels feature. Trace normalization and deduplication
through validation, lookup, and mutation. Give expected results
for clearing labels, invalid input, missing tasks, and filtering.
Map each step to a check. Leave the files unchanged.
```

Review the plan before editing. The limit is ten distinct labels after normalization, so a raw array can have eleven copies of the same label and still be valid. An empty array clears labels. Invalid input must preserve existing labels and must return `400` even for an unknown task. Valid input for an unknown task returns `404`. A present blank filter returns an empty list.

Creation and list responses keep `id` and `title` and add `labels`. Someone whose client accepts only the original keys could see a compatibility break. Include that case in the rollout discussion before accepting the plan.

## Implement and check the behavior

Switch to **Build** with the approved plan. Ask it to keep the existing acceptance criteria visible while it works.

```text
Implement the reviewed in-memory labels plan in src/app.ts. Update
the existing task response assertions for the labels field and keep
their title and invalid-input checks. Leave contracts/labels.test.ts
unchanged. Run npm test and npm run test:labels separately. Show me
the changes and the observed result of each command.
```

After the supplied contract passes directly, ask Build to add this import so the ordinary suite runs it too.

```typescript title="test/labels.test.ts"
import "../contracts/labels.test.ts";
```

Ask Build to add focused coverage for ten distinct labels and for a raw array that collapses to one normalized label. Review each assertion against the input and expected result. Then check the same coverage policy CI will compare with the base.

```sh
npm test
npm run test:labels
node tools/coverage.mjs --base "$(git rev-parse capstone-base)"
git diff --check
git diff --exit-code capstone-base -- contracts/labels.test.ts
git diff capstone-base -- src/ test/
```

If coverage fails, open the report and ask Build which observable behavior would reach the uncovered branch. Protect behavior that matters to the contract. Have the person who owns the gate review any policy or test selection change independently. If you need a worked implementation to compare against, inspect `git diff lab-harness lab-labels -- src/ test/` after reviewing your own diff.

Start a fresh local service with `PORT=3100 npm start`. From a second terminal, run the update, read the task back, and check whether rejection changes stored state.

```sh
curl -sSi -X PATCH http://127.0.0.1:3100/tasks/1/labels \
  -H 'Content-Type: application/json' \
  -d '{"labels":[" Urgent ","bug","urgent"]}'
curl -sSi 'http://127.0.0.1:3100/tasks?label=urgent'
curl -sSi -X PATCH http://127.0.0.1:3100/tasks/1/labels \
  -H 'Content-Type: application/json' \
  -d '{"labels":[" "]}'
curl -sSi 'http://127.0.0.1:3100/tasks?label=urgent'
```

The two reads should show the same task with `["urgent","bug"]`. The invalid update returns `400` with `invalid_labels`. For the strict client case, check the keys of the first task against its old contract.

```sh
node --input-type=module - <<'JS'
const tasks = await (await fetch("http://127.0.0.1:3100/tasks")).json();
const keys = Object.keys(tasks[0]).sort();
console.log(keys.join(", "), "accepted by the old exact-key check:", keys.join(",") === "id,title");
JS
```

Expect the check to report `false` because the response includes `labels`. Record the compatibility finding with the adoption decision from the RFC. Stop the service and inspect the diff. If the changed files match your approved scope, stage and commit the source and tests on `task-labels`.

```sh
git status --short
git add -- src/app.ts test/app.test.ts test/labels.test.ts
git diff --cached --check
git diff --cached
git commit -m "Add searchable task labels"
```

## Review and verify the result

Bring the [reviewer profile](/books/hands-on-coding-assistants/chapters/custom-agents-and-sub-agents/#give-the-reviewer-a-different-job) from the independent-review exercise. If your branch name differs, use that name in the command. If you entered here directly, create the profile from that section. The reviewer needs read access to `specs/`, `contracts/`, `src/`, `test/`, and the saved patch.

```sh
mkdir -p .opencode/agents notes
git show reviewer-exercise:.opencode/agents/reviewer.md > .opencode/agents/reviewer.md
git diff capstone-base HEAD > notes/review.patch
git rev-parse capstone-base HEAD
```

Open a fresh **reviewer** session with these inputs.

```text
Read specs/task-labels.md, contracts/labels.test.ts, and notes/review.patch.
Check the normalized limit, state after a rejected update, and the
shape of the existing responses. Inspect the relevant tests. For each
finding give the criterion, the changed line, and a concrete request
with its expected and inferred results.
```

Check the reads and reproduce any finding yourself. If the report has no findings, keep that result and select a contract case to verify independently. After a correction, rerun the checks, commit the change, and regenerate the patch so the reviewer and CI can refer to the revised head.

### Check the proposed revision in CI

Use the process from [Required CI Checks and Merge](/books/hands-on-coding-assistants/chapters/required-ci-checks-and-merge/). Confirm `origin` points to your fork. Push the two branches and open the pull request within that fork.

```sh
git push -u origin capstone-base
git push -u origin task-labels
```

Target `capstone-base` with an active ruleset that requires **verify (Node 24)**. If the check needs an initial run before you can select it, use the passing-PR setup from that chapter. Inspect the verification log and the merge section. Record the head, base, checked-out revision, and whether the required job passed. Look for the labels cases in the job output to confirm that the verification ran the new contract.

### Check the running gateway

With `task-labels` checked out, start the live stack as in [Instrument the Service and Verify the Alert](/books/hands-on-coding-assistants/chapters/instrument-the-service-and-verify-the-alert/). Wait for the gateway's metrics endpoint to respond, record its starting counts, and replay the update and filtered GET against port `3400`. Check that the filter still returns task 1 with the normalized labels.

```sh
docker compose -f observability/compose.yml -f observability/compose.alerts.yml up -d
```

```sh
curl -fsS http://127.0.0.1:3400/metrics | grep '^lab_task_gateway_requests_total'
date -u
curl -sSi -X PATCH http://127.0.0.1:3400/tasks/1/labels \
  -H 'Content-Type: application/json' \
  -d '{"labels":[" Urgent ","bug","urgent"]}'
curl -sSi 'http://127.0.0.1:3400/tasks?label=urgent'
curl -fsS http://127.0.0.1:3400/metrics | grep '^lab_task_gateway_requests_total'
```

Record the request times and give them to **Plan**.

```text
Use the times I recorded for the successful PATCH and filtered GET.
Give me a Loki query for the live gateway and tell me how to find
each trace by ID. Name the fields to check for status, route template,
and any raw task ID or label filter. Wait for my results.
```

In Grafana, open the matching logs and traces. Expect status `200` and the route templates `/tasks/:id/labels` and `/tasks`. With no other traffic, the `2xx` counter should increase by two. Read the raw log and span attributes to verify that they use the templates and omit the raw task ID and filter value. Save the trace IDs and query results. Remove the lab stack after verification.

```sh
docker compose -f observability/compose.yml -f observability/compose.alerts.yml down -v
```

## Record the merge decision

Keep the local reviewer setup and review record on a separate evidence branch from the tested feature. Give **Build** the verified results and ask for a shareable note. Keep the decision with the PR and link it to the exact revision you checked.

```text
Use the reviewed evidence I pasted to write notes/capstone-review.md.
Record the implementation scope, spec and design references, tests,
reviewer findings and any correction, CI revision and status, and
runtime evidence. Mark remaining checks as pending. Propose a merge
decision with the evidence for it and change only the note.
```

Read the note against the evidence. If you measured the work, include the time you spent verifying and correcting the result. A teammate should be able to recreate the diff, look up the CI run, and repeat the request you checked. Commit the evidence separately if you want to keep it with the lab, and share the reviewed findings in the PR.

```sh
git switch -c capstone-evidence
git add -- .opencode/agents/reviewer.md notes/review.patch notes/capstone-review.md
git diff --cached --check
git diff --cached --stat
git commit -m "Record the task labels merge decision"
```
