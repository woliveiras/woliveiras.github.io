## Your prompt derives from your spec

“Fix registration” gives a model room to guess. It might change the email format, add a new field, or return a different status code. Each choice looks reasonable until you compare it with the existing clients and the acceptance tests.

Use the spec to decide what you need from the prompt. State the task, point to the files that establish context, give the boundary for the change, and name the evidence you expect. The assistant can read the full spec. Your prompt can stay short.

```text
Implement specs/registration-validation.md in src/app.ts. Read the
acceptance test before editing. Keep the existing response shape and
leave contracts/ unchanged. Run npm test and npm run test:registration
as separate commands. Report the result of each and any criterion you
could not verify.
```

## Give feedback the agent can use

When the assistant runs the tests and one fails, send the first relevant assertion and the condition you expected. For example, a valid request received ID `2` after an invalid request. That points to mutation order. It gives the model something to inspect without asking it to rewrite the entire handler.

When it suggests another dependency, ask what behavior in the spec needs it. In this exercise, normalization and a simple address check fit inside the existing route. If a proposed change crosses a boundary in the spec, decide whether to expand the work before asking for another patch.

For a review prompt, ask the agent to name a scenario the diff would get wrong. Require the file and line, the expected result, and the observed or inferred result. You can then reproduce the scenario with an assertion.

## Compare three prompts on one task

Use three fresh Plan sessions with the same model and the same starter state. Send these in order:

1. “Fix the registration endpoint.”
2. “Read `src/app.ts`. Plan a change that rejects invalid names and email addresses before storing a registration.”
3. “Read `specs/registration-validation.md` and `contracts/registration.test.ts`. Plan the route change, list the files, and explain how you will verify that invalid requests leave the next ID available.”

Read each plan beside the acceptance test. Count the plan's unsupported assumptions and the acceptance criteria it omitted. Open the tool activity to check which files it read. Then repeat the best prompt with the other model path, if both are available.

One useful outcome is a prompt that works with both models and still makes a weak response easy to spot. Keep that prompt with the task. If you need to rerun the exercise, you'll know which instructions produced the diff and which were added later.
