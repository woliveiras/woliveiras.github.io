## Decide what the agent needs for this task

The registration task needs a spec, the route, the test, and the ability to run two test commands. An issue link, a GitHub token, and access to your home directory add nothing to this exercise. Starting with that list makes the permission decision much easier.

Open the lab as its own Git repository. Use the source and sample data that came with it. If you're using a hosted provider, the model request may include project context and tool results. With local inference, the model call can stay on your machine. A local model can still ask its harness to reach the network or run a command, so look at the tools and permissions too.

## Keep instructions, tool controls, and isolation distinct

| Concern | Control to inspect |
| --- | --- |
| The agent edits an acceptance test to make a change pass | Review the Git diff and deny mutation of contract paths when the workflow calls for it |
| The shell command does more than the prompt described | Allow only known commands for that task and review any approval request |
| The input contains a credential or client data | Keep it out of the lab, prompts, and tool outputs |
| A subprocess needs stronger containment | Run the task under a constrained account, sandbox, or isolated environment suited to the risk |

The lab config explicitly denies outside-directory access for tools that honor OpenCode's boundary checks. The shell still runs with the underlying process's privileges. A shell script can do more than appears in its command name, so read project scripts before allowing them by name. For work that needs containment at the operating-system level, restrict the environment and credentials available to the process.

## Test the boundary without introducing sensitive data

In a disposable copy of the lab, add this entry at the end of the `permissions` array:

```jsonc
{ "action": "edit", "resource": "contracts/*", "effect": "deny" }
```

Start a fresh **Build** session and ask for a harmless one-line comment in `contracts/registration.test.ts` specifically to exercise the rule. A text refusal without an attempted edit doesn't demonstrate enforcement. If the tool reports a permission denial, check `git diff -- contracts/` and confirm no change. Remove the test request from your task context before continuing with the real exercise.

Then inspect the project commands. The starter can run from a fresh archive without downloading dependencies. In a real repository, review dependency additions, lockfile changes, install scripts, and newly introduced services as part of the patch. Decide who can approve an action before wiring an agent into it.

## Treat retrieved text as project input

An issue description, a README, and an MCP tool result can contain directions that conflict with your task. A useful first defense is to scope tools to the job and review a new instruction before granting access it asks for. If a tool result asks for an unrelated command or credential, stop and inspect its source. Keep action policy in configuration you control.

Model output also needs the same provenance and licensing review as other contributed code. For the lab, record which code the model proposed and which changes you verified. In a team, follow the repository's review and attribution rules for the code you ship.
