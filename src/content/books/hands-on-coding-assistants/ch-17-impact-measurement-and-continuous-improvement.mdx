## Count the whole change

A model can generate a patch quickly and consume the time you saved during review. Measure from the first read of the task to the point where you have a change you'd accept. Include the time spent clarifying the plan, rerunning a test, and investigating an unexpected edit.

A randomized study of experienced open-source developers on familiar codebases found that the AI-enabled condition took longer in that setting. Use it as a reason to measure your own workflow, where the model, task, and review burden will differ.

## Compare manual and delegated setup

Return to the [registration exercise](/books/hands-on-coding-assistants/chapters/the-spec-first-workflow/#the-spec-first-workflow). Creating the branch and checking the starting tests is a complete task on its own. You already know the commands and what they should show. That makes it a good place to see what delegating adds.

Use two clean copies of the lab at the same starter commit. Set up OpenCode and the model before timing, and note the model ID. In the first copy, run these commands yourself:

```sh
git switch -c registration-validation
npm test
npm run test:registration
```

In the second copy, open a fresh **Build** session and give the agent the same job. If OpenCode asks to run `git switch`, review the command and approve it once for this exercise.

```text
Use the shell tool to run these commands separately, in order, from
the current checkout. The last test command is expected to fail on
the starter. Report what each command actually did and its exit
status. Leave the source and tests unchanged.

git switch -c registration-validation
npm test
npm run test:registration
```

In both runs, verify that the branch is `registration-validation` and that `git status --short` is empty. Check the exit statuses yourself or in the session's tool output. The branch command and `npm test` should succeed. The registration contract should fail because the starter has yet to implement validation.

| Record | How to measure it |
| --- | --- |
| Elapsed time | Start before typing the first command or putting the prompt into OpenCode. Stop after verifying the branch, test results, and working tree. Include approvals, waiting, and any follow-up. |
| Calls and retries | Count shell attempts and visible model steps separately. Record denied commands, retries, and any extra requests. Use provider usage records if you need the actual number of billed requests. |
| Tokens and spend | Record reported token categories and any charge you can verify. Use zero model calls and tokens for the manual run. Mark unavailable data as unknown. |
| Review and intervention | Note what you checked yourself, what you had to correct, and whether the agent found anything that changed your next step. |

For the delegated run, list your sessions and export the matching one after timing. Replace `YOUR_SESSION_ID` with the ID of the run you just checked. The exported session's `info.tokens` contains the observed token totals when usage is available. Keep input, output, reasoning, and cache fields separate. A billing record is the source for what the provider actually charged.

```sh
opencode session list
opencode session export YOUR_SESSION_ID --sanitize > ../agent-setup-session.json
```

In a check of this exercise, OpenCode ran the requested commands, and the hosted model hit a free usage limit before it could summarize them. The shell output still showed the baseline passing and the contract failing. If that happens to you, record where the run stopped and which results you could verify.

## Account for energy, water, and local impacts

A free quota tells you what the provider charges for access. The agent's model calls still use computing resources. Electricity use for a task varies with the workload and the infrastructure that runs it. On your own machine, a plug-in power meter can give you watt-hours for the whole machine during the run. Measure a separate idle interval of the same duration if you want to estimate the extra electricity above baseline. For a hosted run, use provider measurements with a comparable scope if available. Keep energy use unknown when your evidence is limited to tokens and call counts.

Electricity is one part of the environmental picture. The Berkeley Lab report separates water used at a data center, mainly for cooling, from water used to produce its electricity. The emissions and water impacts associated with that electricity depend on the local generation mix. Estimating those impacts for a specific run calls for information about where it ran, its electricity use, and the cooling it relied on.

There is also a question of who experiences the effects. Virginia's legislative review documents impacts that vary by site, including some nearby residents reporting that persistent data center noise affects their well-being. It also identifies local tax revenue and economic benefits concentrated in construction. Those findings describe the places the commission studied. Look for local evidence when assessing who benefits and who bears costs near a particular facility.

Use the comparison to decide where a model call earns its place in your workflow. A known test command is easy to run directly. An unfamiliar failure may warrant an agent that can connect the output to the code. Record what its work helped you decide alongside the time and usage it took to get there.

## Compare the same task

For the full registration change, compare implementation runs across models.

Use a clean copy of the registration starter for each run. Keep the spec, prompt, and acceptance tests the same. Decide in advance what counts as completion. For this exercise, both test commands passing and a reviewed diff limited to the route meet that bar.

| Record | How to observe it |
| --- | --- |
| Setup and task time | Record model download or provider setup separately from time spent on the change |
| Scope | Record the edited files and any proposed work outside the spec |
| Correctness | Record the actual exit status of the baseline and feature tests |
| Interventions | Record when you correct a plan, redirect a tool call, or repair a patch |
| Review effort | Record the time and checks required to accept the diff |

Note the OpenCode version, model ID, context settings, starting commit, and platform with each run. Hosted limits and a cold local model can both affect elapsed time. If you run both models yourself, alternate the order on repeated attempts. The first attempt teaches you about the exercise and can make later attempts easier.

## Change one part of the harness

If an agent repeatedly guesses the test command, make it easier to find. If the same requirement goes missing from otherwise good plans, improve the spec or add a test. If extra tools take up context without helping, remove one and repeat the task.

Write down the change and the result. For example, you could add the path to the registration contract to the prompt, then see if the next run catches the distinction between rejecting input and avoiding the state change. A single exercise gives you a case you can inspect. Repeat on different tasks before treating it as a finding about the whole team.
