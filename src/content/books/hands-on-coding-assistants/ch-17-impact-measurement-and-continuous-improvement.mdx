## Count the whole change

The task is complete when you can accept the result. Time spent reading a diff, correcting a missed requirement, or rerunning a check belongs in that measurement. A randomized study of experienced open-source developers found that participants took longer with the early-2025 AI tools available in that study. Use the lab to measure your own workflow and find where you spend the time.

You'll compare running two checks yourself with asking OpenCode to run them. Then you'll change one part of an implementation prompt and see what it does to the work you have to review.

## Compare manual and delegated checks

From the root of your fork, create a branch for the measurement record and two clean worktrees from the same starter commit. Use the same Node version in both and record it.

```sh
git switch -c measurement-record lab-start
mkdir -p notes
git worktree add --detach ../task-api-manual lab-start
git worktree add --detach ../task-api-delegated lab-start
git -C ../task-api-manual rev-parse HEAD
git -C ../task-api-delegated rev-parse HEAD
node --version
```

Use a timer or note the start and end times. Start when you are ready to run or delegate the checks. Stop after you can report both results and verify the checkout is clean. From the manual worktree, run each of these commands and record its exit status immediately after it returns.

```sh
npm test
echo "$?"
npm run test:registration
echo "$?"
git status --short
```

Expect three passing base tests with exit `0` and two failing contract tests with exit `1`. A correct report on the starter includes the failure. In the delegated worktree, open a fresh **Plan** session with the model you want to measure. Record its ID and send this prompt.

```text
Run npm test and npm run test:registration as separate shell calls.
Use the exact commands. Report the observed status and test result
for each. Leave the repository unchanged.
```

Read the tool results. If the agent runs only one command, include the time spent asking again and verifying the new output. If a quota or denied call prevents completion, record the interruption and the results you were able to confirm. Check `git status --short` in the delegated worktree yourself.

| Record | Where to check it |
| --- | --- |
| Elapsed time | Start through final verification, or through the recorded interruption |
| Test outcome | The two commands, exit statuses, and the observed failure |
| Interventions | Retries, approvals, later prompts, and checks you ran yourself |
| Usage | Model and runtime versions, reported token categories, and any available charges |

OpenCode's session export can supply usage fields when the client receives them. Inspect the export before sharing it, as in the [prompt exercise](/books/hands-on-coding-assistants/chapters/prompt-engineering-for-code-assistants/#keep-a-record-that-survives-the-session). Keep input, cached, output, and reasoning counts distinct. A teammate should be able to tell which run is comparable even if one field is missing.

## Change one thing

Use two more clean worktrees at `lab-start`. From the fork root, create a branch for each run so you can keep its diff. The task is to implement registration validation. Keep the same model, permissions, spec, and acceptance checks in both.

```sh
git worktree add -b measure-spec-only ../task-api-spec-only lab-start
git worktree add -b measure-spec-and-contract ../task-api-spec-and-contract lab-start
```

Open a fresh **Build** session from the first checkout.

```text
Read specs/registration-validation.md and implement it in src/app.ts.
Keep the supplied tests unchanged. Run npm test and
npm run test:registration, and report the observed results.
```

In the second checkout, send the same prompt with one additional sentence directly after the first.

```text
Read contracts/registration.test.ts before editing.
```

Use the same finish condition for both runs. The two suites must pass and you must be able to accept the diff against the spec. Inspect the file reads as well. If both sessions discover the contract before the edit, record that outcome. If you had to supply the next-ID requirement, record when you supplied it and how you verified the correction.

Paste a row for each run into **Plan**. Include elapsed time, the exit status of both commands, and whether you accepted the diff for each implementation. The agent needs those results to know which runs reached the same finish condition.

```text
Use the results I pasted. Compare only runs with the same finish
condition. Show where time or interventions differed and which
differences are visible in the tool activity. Propose one adjustment
I can test on a repeat run. Keep uncertainty in the report.
```

Check the suggested adjustment against the evidence. Alternate run order on a repeat so familiarity with the first result has less influence. Keep interrupted runs as part of the record, with the outcome clearly marked. In each implementation worktree, review and commit the diff you tested. Return to the fork root and save the measurements, exact prompts, revision IDs, and your chosen adjustment in `notes/measurement.md`. If you ask Build to save it, give it that relative path and open the file there before you continue.

```sh
git branch --show-current
git status --short --untracked-files=all
git add -- notes/measurement.md
git diff --cached --check
```

Check that you are on `measurement-record` and the staged file is the intended note. If the tool wrote a copy under a different path, move the reviewed file to `notes/measurement.md` and stage it again. Once all four worktrees are clean and their OpenCode sessions are closed, commit and remove them.

```sh
git commit -m "Record the Task API measurement exercise"
git worktree remove ../task-api-manual
git worktree remove ../task-api-delegated
git worktree remove ../task-api-spec-only
git worktree remove ../task-api-spec-and-contract
```

## Account for energy, water, and local impacts

A local wall meter can give you energy for the whole machine during the measured interval. Record what else was running. If you measure an idle interval of the same length, document it before estimating the additional energy. For a hosted run, report energy as unknown unless you have a provider measurement with comparable scope. Token counts describe model usage.

Broader impacts use different measurements. Berkeley Lab distinguishes water used directly at a data center from water associated with its electricity supply. The IEA report describes electricity demand and grid constraints. A Virginia legislative review documents local economic benefits and reported effects of persistent noise at some sites. Keep each conclusion tied to the scope of its source.

In the [final project](/books/hands-on-coding-assistants/chapters/end-to-end-final-project/), you can recover this note with `git show measurement-record:notes/measurement.md`. Use the same finish condition to record where review and verification took time. Those observations can guide which controls you keep for the next change.
