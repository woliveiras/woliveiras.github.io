## Put the check where it will run

The assistant can run `npm test` and still describe a change you haven't reviewed. A deterministic hook gives you a separate checkpoint. The lab combines a staged diff check with the baseline tests. The feature's contract remains an explicit command for the branch you're working on.

From the lab's Git root, create `.githooks/pre-commit`:

```sh title=".githooks/pre-commit"
#!/bin/sh
set -eu
git diff --cached --check
npm test
```

Enable it for this repository:

```sh
chmod +x .githooks/pre-commit
git config --local core.hooksPath .githooks
```

Use Git Bash for these shell examples if you work on Windows. Git runs the pre-commit hook before creating a commit and stops if it exits unsuccessfully. `npm test` runs against the working tree, so review unstaged changes alongside the staged diff. A clean checkout in CI is the place to verify exactly what was committed.

## Watch a failing check stop a commit

Use a disposable branch with the starter committed. Add a blank line containing spaces to the end of `README.md`, stage that file, and try to commit it. The whitespace check should fail. Inspect the staged diff, remove the spaces, stage the fix, and retry. The hook should now reach the tests.

On a feature branch run the feature contract before asking for review:

```sh
npm run test:registration
```

If you're working on task labels, use `npm run test:labels` instead. Those commands fail on the starter by design. Once a feature lands, a maintainer can move its assertions into the regular test suite so every subsequent change runs them.

## Where an OpenCode hook fits

A Git hook sees a repository event. An OpenCode plugin can observe a tool event inside the harness, for example `execute.after` to record the outcome of a tool call. That can help explain which check the agent attempted. Keep the actual pass or fail decision in the check that you and CI can both run. OpenCode 2's plugin API has a different shape from v1, so use the API reference for the version you're running.

To see the difference, create `.opencode/plugins/lab-check-marker.js` in the lab. This small plugin attaches a marker to a completed shell tool call. The tool's response and exit information stay available for inspection.

```javascript title=".opencode/plugins/lab-check-marker.js"
export default {
  id: "lab-check-marker",
  async setup(ctx) {
    await ctx.tool.hook("execute.after", event => {
      if (event.tool === "shell" && event.status === "completed") {
        event.result = {
          ...event.result,
          metadata: { ...event.result.metadata, labCheckObserved: true },
        };
      }
    });
  },
};
```

Run a new session and ask the agent to execute the exact test command:

```sh
opencode run --format json "Use the shell tool to run npm test in this project. Report the exit status."
```

Find `labCheckObserved` in the shell tool's output event. Use the event's test output to determine whether the command passed. A completed call is one the harness handled, and the command itself can still return a failing exit status. The Git hook reads that status directly.
