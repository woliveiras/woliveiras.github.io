When you ran `/check-spec`, you supplied the task and chose the prompt to run. A **skill** packages instructions for a kind of work. OpenCode can advertise its ID and description, then load its body when the agent calls the skill tool. Use one when the procedure recurs across tasks and needs more detail than the project guidance you load at startup.

Start a fresh branch at `lab-start` and open **Plan**. Give it a request that still has unanswered product questions.

```sh
git switch -c spec-writing-skill lab-start
opencode
```

```text
A user wants to download their tasks to open in a spreadsheet.
Draft a Task API feature spec. Identify what still needs a decision.
Return it in chat.
```

Keep the draft. The request leaves the file format, columns, and which records to include open. A draft can describe those decisions and ask the owner to settle them.

## Add the procedure

Create the skill directory in your fork.

```sh
mkdir -p .opencode/skills/spec-writer
```

Save the following file. The directory sets the ID `spec-writer`, and the description tells the model when the procedure applies.

```md title=".opencode/skills/spec-writer/SKILL.md"
---
name: spec-writer
description: Draft a Task API feature spec with observable criteria and explicit open decisions.
---

Read the feature request and the relevant route in the repository's
src/app.ts. Return a draft with Goal, Acceptance criteria,
Verification, and Open questions. Under Verification, give a
concrete input and expected outcome for each decided criterion.
Ask about the visible effect of rejection wherever the feature
can change stored state. Leave unanswered decisions in Open questions.
```

Reopen OpenCode and use the same model in a fresh **Plan** session.

```text
Use the skill tool to load spec-writer. A user wants to download
their tasks to open in a spreadsheet. Draft a Task API feature
spec. Identify what still needs a decision. Return it in chat.
```

Check for a completed `skill` call with the ID `spec-writer`. Then compare the drafts. Look for a concrete verification step for each settled criterion and for questions about format and scope. If a draft promises CSV, ask what part of the request settled that choice. Save the answer and the tool observation together so you can tell what the skill contributed.

## Check the permission boundary

Append this rule to the `permissions` array in `opencode.jsonc` for a comparison.

```jsonc
{ "action": "skill", "resource": "spec-writer", "effect": "deny" }
```

Reopen OpenCode and repeat the same request in a fresh **Plan** session. The skill should be unavailable or the load should be denied. A draft can still be produced from the prompt. Record whether there was a completed skill call. Remove the test denial, reopen OpenCode, and check that the skill loads again.

Review the skill body and any resources it directs an agent to use before sharing it. Record the successful and restricted runs, then commit the skill on `spec-writing-skill`.

```sh
git diff --exit-code -- opencode.jsonc
git add -- .opencode/skills/spec-writer/SKILL.md
git diff --cached --check
git commit -m "Add the Task API spec-writing skill"
```
