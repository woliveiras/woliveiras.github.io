Someone asks you about a new feature: “Let people mark tasks as urgent and find them again.” That's enough to start a conversation. But it leaves open what a client sends, whether existing clients accept a new response field, and what happens to labels on a restart.

An **epic** groups work that takes several deliverable changes. Start with a small release you can explain to a reviewer. Use the current Task API, the map from [Exploring an Unfamiliar Codebase](/books/hands-on-coding-assistants/chapters/exploring-an-unfamiliar-codebase/) and the verified fix from [Debugging](/books/hands-on-coding-assistants/chapters/debugging-refactoring-and-iteration/). Keep these design artifacts on one branch.

```sh
git status --short
git switch -c design-task-labels debug-registration
git show read-task-api:notes/repo-map.md > notes/repo-map.md
opencode
```

The copied map describes the starter. Keep its original revision in the note, and use the registration fix as the baseline for describing the current service.

## Separate work you can start from decisions you need

Use **Plan**. Give it a brief with enough friction to reveal the dependencies.

```text
A Task API consumer needs to replace the labels on a task, clear them,
and find tasks by one label. The first release runs in the lab and keeps
the in-memory store. One existing consumer may validate task responses
strictly. A later release will need to keep labels across restarts.

Read notes/repo-map.md and src/app.ts. Identify open decisions and
propose a backlog for the first release. Each item needs a title,
description, acceptance checks, dependencies, complexity and a range
in engineering hours. Mark assumptions, and keep the durable storage
decision visible as follow-up work. Return the draft in chat.
```

Check the dependency direction. Two changes can start after a shared contract is agreed, but they both need to be ready before the end-to-end check. If the agent puts compatibility at the end without asking about strict clients, move the contract investigation earlier. A quick sample decode can change the API plan.

## Write tickets someone else can pick up

Draft the feature goal, open decisions, and tickets in the same Plan session. Use a stable local ID for each ticket so you can record which one blocks another. Jira accepts time estimates and linked work items. You can do this exercise entirely in the repository.

One ticket can read like this.

```markdown
### LABEL-2 — Replace labels on a task

Add PATCH /tasks/:id/labels to replace the list. Apply the agreed
normalization before storing it. Keep storage inside the Task API.

Acceptance checks
- Replacing labels returns the resulting list in first-seen order.
- An empty array clears the list.
- A rejected payload keeps the previous list available on the next read.

Depends on LABEL-1 for response shape, normalization and error rules.
Complexity M. Estimate 8–12 engineering hours. The range includes HTTP
tests and review. The lower end assumes the existing client accepts the
agreed response shape.
```

Review the other tickets for the same level of detail. For example, arrange the work around these finish conditions.

| ID | Work and acceptance check | Depends on | Complexity | Engineering hours |
| --- | --- | --- | --- | --- |
| LABEL-1 | Decide and test the response shape against a representative existing client. Write down the normalization and error rules. | — | S | 4 |
| LABEL-2 | Replace and clear labels. Rejection preserves state. | LABEL-1 | M | 8–12 |
| LABEL-3 | List tasks filtered by one normalized label. Test an omitted filter and a filter that matches nothing. | LABEL-1 | M | 8–12 |
| LABEL-4 | Exercise update and filter together. Record the rollout and reversal checks. | LABEL-2, LABEL-3 | S | 4 |

Complexity describes how hard the work is to reason about. Hours estimate effort under the assumptions you wrote down. Treat the compatibility investigation as a decision point. If it reveals a breaking change, revise the tickets and the forecast before treating the proposal as ready.

## Change a constraint and recalculate

There are 24–32 engineering hours in this example. With two people who each have four focused hours a day, assign LABEL-2 and LABEL-3 to separate people after LABEL-1. The longest required chain is LABEL-1, the longer of the two middle items, then LABEL-4. The range is four to five workdays. With one person at the same daily capacity, the work takes six to eight days. If an external compatibility decision adds up to two days of waiting on that chain, the two-person forecast becomes four to seven days. These are example ranges under stated assumptions. The GAO calls the longest chain that governs the finish date the critical path.

Ask Plan to recompute the schedule for one person and one external wait. Check the sums yourself and decide which assumptions you'll keep. Then switch to **Build** in the same session.

```text
Save the reviewed backlog and forecast as notes/task-labels-epic.md.
Give each ticket its own description, acceptance checks, dependencies,
complexity, and estimate. Include the capacity assumptions and explain
how the compatibility decision affects the forecast. Keep the durable
storage follow-up visible. Change only the epic note.
```

Read the saved note and check that each dependency points to an existing ticket. Commit the map and backlog together.

```sh
git add notes/repo-map.md notes/task-labels-epic.md
git diff --cached --check
git commit -m "Plan the task labels epic"
```

Keep the compatibility and durability questions in the epic. Next, [document the system](/books/hands-on-coding-assistants/chapters/automated-documentation/) on this branch. The [RFC](/books/hands-on-coding-assistants/chapters/write-and-review-an-rfc/) uses those diagrams to show what the proposal would change.
