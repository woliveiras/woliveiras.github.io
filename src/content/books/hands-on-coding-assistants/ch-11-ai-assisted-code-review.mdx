## Bring the evidence to the reviewer

A passing test suite is one part of a review. On the registration branch, the diff also needs to leave unrelated routes intact and validate before assigning an ID. Review those properties against the original spec.

Run these commands in the lab before asking for a review:

```sh
git status --short
git diff --check
git diff -- src/app.ts
npm test
npm run test:registration
```

If you've already staged the change, inspect `git diff --cached` too. The reviewer in [Custom Agents & Sub-Agents](/books/hands-on-coding-assistants/chapters/custom-agents-and-sub-agents/) is configured for the unstaged diff. Give it a diff you can both refer to.

## Ask for findings you can reproduce

Start the read-only reviewer in a fresh session with this request:

```text
Review the registration change against specs/registration-validation.md.
Check that invalid requests leave the next ID available, valid responses
return the normalized fields, and no unrelated response changed.
For each issue, give the changed line, an example input, and the expected
versus observed behavior. Label anything you inferred from reading.
```

When the reviewer calls something “insecure” or “incorrect,” ask which observable behavior is wrong. A proposal to require email verification would add a new product requirement. A rejected request that advances the ID would violate the existing one. The spec gives you a way to decide which comment belongs in this change.

## Verify a finding before asking for a fix

Reproduce the input locally or add a focused regression test when there is a missing case. If you confirm the issue, carry that evidence into Build. Ask for a correction limited to what the finding demonstrates. Run the same suite and read the new diff.

In the local registration pilot, the first implementation passed the initial tests. The diff checked for a literal space and looked for a dot anywhere in the email. That let a tab slip through, and it could count a dot before the `@` toward the domain rule. The expanded contract includes both cases. A green run only covers the cases it exercised. Reading the diff against the spec exposed the gap.

If a reviewer finds nothing, compare the scope it actually inspected with your checklist. A missing read tool call or an empty diff explains some quiet reviews. Treat the review summary as a record of what was checked and make the merge decision yourself.

## Review the model as well as the patch

Try the same request with the local and hosted paths on one diff. Note which comments you could verify, which repeated the spec, and which would have sent the implementation away from it. This is more useful than comparing comment counts. It tells you which kind of review the setup can help you with.
