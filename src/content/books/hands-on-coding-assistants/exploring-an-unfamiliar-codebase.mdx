## Start with a question about the application

Where does a task live between `POST /tasks` and `GET /tasks`? The answer tells you where to look when a write appears to succeed, which code a change might affect, and whether the data will still be there after a restart.

Open the starter in OpenCode using the model you selected in [the setup chapter](/books/hands-on-coding-assistants/chapters/setup-and-practical-integration/). Choose **Plan** for this session. OpenCode's Plan agent can inspect the project and blocks edits to ordinary project files by default. Shell commands still follow the configured permissions. Run `git status --short` in your terminal before and after the exercise so you can check the workspace yourself.

## Sketch the architecture from entry points

Give the agent a small investigation with a defined scope:

```text
Read AGENTS.md and package.json. Use file reads and search to find what
npm start and npm test load. Follow both paths to the HTTP application.
Show where a task is stored. Cite a file and symbol for each finding,
label any inference, and leave the workspace unchanged.
```

Open the files it cites. You should be able to follow these two paths to the same application factory:

| Path | Follow it in the code |
| --- | --- |
| `npm start` | `package.json` starts `src/server.ts`. That entry point calls `createApp()` and listens on `127.0.0.1`. |
| `npm test` | `test/app.test.ts` uses `startApp()` in `test/client.ts`. The helper calls the same factory and lets the OS choose a port. |

In `src/app.ts`, `createApp()` creates a `tasks` array and returns the HTTP server that reads and writes it. Starting a new instance of the lab creates a fresh array with the starter task. If the agent mentions a database or tells you every test starts the command-line server, ask it to show the call in the code. Then check the factory and the test helper yourself.

## Trace a request from input to response

Keep the same session and narrow the question:

```text
Trace POST /tasks with the JSON body {"title":" "}. Find where the
request body is read, where the title is normalized, and where the route
returns. Does it reach the line that adds the task? Name a test that
checks both the response and the stored state. Leave files unchanged.
```

Follow `readObject()` to the route's `trim()` call. The empty result triggers HTTP 400 with `{"error":"invalid_task"}`. That branch returns before `tasks.push(task)`. In `test/app.test.ts`, the blank-title test checks the error and then sends `GET /tasks` to verify the list still contains only the starter task.

Run the test yourself from the lab directory. One test should pass:

```sh
node --test --test-name-pattern='a blank task title' test/app.test.ts
```

The source establishes the path through the handler. The test exercises one input and its observable effects. Keep those two pieces of evidence attached to the explanation when you ask a follow-up.

## Ask the question that leads to the spec

Compare the task route with `POST /registrations`. Ask which parts of the flow they share and what happens when the registration name is a number. Have the agent point to the line that handles the value and the line that changes state. Keep the question about the starter's current behavior.

Your notes should be enough for another developer to reproduce what you saw. Record the entry point, the relevant handler, the state change, and the test or source that supports each claim. Write down the decision that still needs a spec. In this lab, that decision is which registration inputs deserve a 400 and what must happen to the next ID. Carry it into [The Spec-First Workflow](/books/hands-on-coding-assistants/chapters/the-spec-first-workflow/).
