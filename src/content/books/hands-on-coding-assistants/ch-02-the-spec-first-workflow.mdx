## The spec-first workflow

In [the exploration chapter](/books/hands-on-coding-assistants/chapters/exploring-an-unfamiliar-codebase/), you traced what happens when `POST /registrations` receives a number as the name. The starter turns the number into a string and assigns the registration an ID. Before changing the route, decide what the caller should receive and what should happen to that ID.

A **spec**, short for *specification*, describes the behavior you want to add or change and why it matters. Its *acceptance criteria* say what you need to observe before accepting the change. For this API, that includes the HTTP status, the response body, and the state you can observe on a later request.

In **spec-driven development**, you write down those decisions before planning the implementation, then use the same criteria to review the plan, the patch, and the tests. If the plan exposes a decision you missed, settle it in the spec before asking for code.

Start with a smaller change in the same lab. A task detail view needs to fetch one task by ID. You'll write the spec and have OpenCode implement it, then carry the same questions about responses and state into registration.

## Write a spec for a new feature

Read `GET /tasks` and the fallback response in `src/app.ts`. The list already exposes each task with an `id` and a `title`, and the fallback returns HTTP 404 with `{"error":"not_found"}`. Use those conventions to decide what the new route should return.

1. **Goal.** Describe what the client needs to do. The detail view needs to load a task when someone opens its URL.
2. **Acceptance criteria.** Write down the status and response body for a known ID and an unknown one. Include what a lookup should do to the stored tasks.
3. **Scope.** Name the route you’re adding and any existing behavior your change must preserve.
4. **Verification.** Name the tests you would add and the command you would run. Use the existing HTTP tests as a starting point.

Draft your version under those four headings, then compare it with the worked spec.

```markdown
# Fetch a task by ID

## Goal

Let the task detail view fetch a single task when it opens from a URL.

## Acceptance criteria

- When a task has the requested ID, return HTTP 200 with its `id` and
  `title`. With the starter's seed data, `GET /tasks/1` returns
  `{"id":"1","title":"Write a spec"}`. Tasks created through
  `POST /tasks` can also be fetched by their IDs.
- When no task has the requested ID, as with `GET /tasks/999` on a fresh
  instance, return HTTP 404 and `{"error":"not_found"}`.
- The task list is identical before and after each lookup.

## Scope

Add `GET /tasks/:id` using the existing in-memory task store. Preserve the
behavior of `GET /tasks` and `POST /tasks`.

## Verification

In `test/app.test.ts`, check the seeded task, a newly created task, and an
unknown ID. Compare the task list before and after each lookup. Run `npm test`.
```

Before handing the spec to OpenCode, try to write the assertions in your head. A test that fetches only task `1` could pass with a hard-coded response. Fetching a task created during the test checks that the route reads from the same store as `POST /tasks`.

## Implement the task lookup with OpenCode

Open a terminal in the Task API lab folder containing `package.json`. From the clean starter checkout, create the lookup branch and run the baseline tests. All three should pass.

```sh
git switch -c task-lookup
npm test
```

Save the worked spec as `specs/task-lookup.md` and run `opencode` from the lab folder. Use `/models` to select the model you verified in [Setup & Practical Integration](/books/hands-on-coding-assistants/chapters/setup-and-practical-integration/#check-file-and-shell-tools). Open `/agents`, select **Plan**, and send this prompt.

```text
Read specs/task-lookup.md, src/app.ts, and test/app.test.ts.
Plan the new GET /tasks/:id route. Explain how it will find tasks in the
existing store and how the tests will check each acceptance criterion.
Flag any open decisions and wait for my review before editing.
```

Read the plan against the spec. Look for both kinds of successful lookup, the established 404 response, and a check of the task list after a read. If the plan exposes an open decision about the API, update the spec and have OpenCode read it again.

Once you approve the plan, use `/agents` to choose **Build** in the same session. Send this prompt.

```text
Implement specs/task-lookup.md using the plan we just reviewed.
Update src/app.ts and add the lookup cases to test/app.test.ts. Preserve the
existing tests and leave contracts/ unchanged. Run npm test and report the
result, including which cases you added.
```

Check the output of `npm test` in the session, then review the patch from your terminal.

```sh
git status --short
git diff --check
git diff -- src/app.ts test/app.test.ts
npm test
```

Check what each assertion proves. The tests should verify the exact responses and compare the list before and after each lookup. During the registration exercise, you'll use the next assigned ID as evidence about state in the same way you used the task list here.

Once the diff matches the spec and the tests pass, close the lookup session. Save the work on its own branch, then return to the starter branch for the next exercise.

```sh
git add specs/task-lookup.md src/app.ts test/app.test.ts
git commit -m "Add task lookup by ID"
git switch -
```

## Prepare the registration exercise

The lookup exercise started with the baseline and added tests from the spec. For registration, the lab already provides an acceptance suite. Create a new branch from the starter and run both suites to see which behavior still needs to change.

```sh
git switch -c registration-validation
npm test
npm run test:registration
```

The baseline passes. The acceptance suite fails on normalization and invalid input. Keep those failures in mind as you write the criteria.

You can also delegate the setup to OpenCode. If you try that from the starter, choose **Build** and ask it to run the three commands in order and report the actual results. I prefer to run small commands like these myself to save tokens, context, and time. In [Chapter 18](/books/hands-on-coding-assistants/chapters/impact-measurement-and-continuous-improvement/#compare-manual-and-delegated-setup), you'll compare both approaches and look at the environmental and community impacts of running models.

## Write down the observable behavior

Return to the question from the beginning of the chapter. Use the four headings from the lookup spec to draft the rules for `POST /registrations`. The goal is to validate the name and email before storing a registration. Give one example of what should be stored and returned for valid input with surrounding whitespace. Then give an example of a rejected request and describe what the next valid request should show.

Compare your draft with `specs/registration-validation.md` and `contracts/registration.test.ts`. Check where the reference spec draws the line on name length and what it considers a valid email. Then find the assertion that corresponds to each result below.

| Input or event | What you should observe |
| --- | --- |
| Valid name and email with surrounding whitespace | HTTP 201 with `id`, a trimmed `name`, and a trimmed, lowercase `email` |
| Missing, mistyped, or malformed fields | HTTP 400 and `{"error":"invalid_registration"}` |
| The first valid request on a fresh server after several rejections | HTTP 201 with `id` equal to `"1"` |

The last check catches a patch that returns the right error after consuming an ID. Include that behavior when you review the plan. Use the supplied spec as the input to OpenCode so that the plan and the acceptance tests are working from the same rules.

## Read the plan before requesting a patch

Run `opencode` from the registration branch and start a fresh session with `/new`. Use the same model you used for the lookup, select **Plan**, and give it the existing contract along with the spec.

```text
Read specs/registration-validation.md, contracts/registration.test.ts,
and src/app.ts. Plan the changes to POST /registrations. Explain where
you will check types, normalize the fields, validate the result, and
assign an ID. Map the steps to the acceptance tests and wait for review.
```

Check that the plan rejects non-string values before trying to normalize them. The name length and email shape checks should use the normalized values, and the error path should return before the code assigns an ID or stores the registration. The spec calls for a change in `src/app.ts` and sets the existing tests as the acceptance contract.

## Implement and review

When the plan matches those criteria, switch to **Build** in the same session and send this prompt.

```text
Implement specs/registration-validation.md using the reviewed plan.
Edit src/app.ts and leave the acceptance tests unchanged. Run npm test
and npm run test:registration and report the observed results.
```

Inspect the patch and repeat the checks from your terminal.

```sh
git status --short
git diff --check
git diff -- src/app.ts
npm test
npm run test:registration
```

Both suites should now pass, and `git status --short` should list only `src/app.ts`. In the diff, follow a rejected request to its return before the ID is assigned. Then trace the normalized values into the stored registration and the HTTP 201 response.

If you're comparing models, repeat registration from the same starter commit in another branch or copy of the lab. Keep the prompts, spec, and tests the same. Record the model ID, the commands it actually ran, their results, and any corrections you had to request.
