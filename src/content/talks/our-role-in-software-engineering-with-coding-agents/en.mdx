<section>
  <h2>Design systems so you can delegate changes</h2>
  <p>The export failed. Why does the screen still say “in progress”?</p>
  <div class="columns">
    <div>
      <h3>Report generator</h3>
      <p>Sends the failure notification.</p>
    </div>
    <div>
      <h3>Request service</h3>
      <p><strong class="takeaway">Delegated fix</strong><br />Record the failure on the request.</p>
    </div>
    <div>
      <h3>Export screen</h3>
      <p>Shows the request status.</p>
    </div>
  </div>
  <div class="signal">
    <p>A test simulates the notification and checks the stored status. Whoever integrates the fix checks that the failure appears on screen.</p>
  </div>
  <p class="source">Sources: <TalkReferencesLink sourceId="r21">Nikolov and Taneja, Google (2024), Accelerating code migrations with AI</TalkReferencesLink> · <TalkReferencesLink sourceId="r23">Cemri et al. (2025), Why Do Multi-Agent LLM Systems Fail?</TalkReferencesLink></p>
  <aside class="notes">
    <p>Back to the fictional export. Imagine the generator already reports failures and the screen already knows how to show “failed.” The problem is in between. The service receives the notification but leaves the request “in progress.”</p>
    <p>The agreement between the three parts bounds the agent’s task. It can fix the service and send a failure notification for a known request to test the result. The engineer integrating the change then triggers a failed test export and checks what the user sees.</p>
    <p>Evidence</p>
    <p>Plan in increments that can be assessed separately. Parallel work needs stable contracts at the boundaries and someone responsible for integration [R07, R20, R23].</p>
    <p>In Google’s large-scale migrations, locating code, changing it, reviewing it and rolling it out are separate steps. Planning accounts for reviewer capacity [R21].</p>
    <p>Multiple agents introduce specification, coordination and verification failures [R23].</p>
    <p>A good sign: each delegated change can be checked on its own, and a boundary contains an agent’s error.</p>
    <p>Refs: R07, R20, R21, R23.</p>
  </aside>
</section>

<section>
  <h2>Verify, review and operate</h2>
  <ul class="lines">
    <li>Which test shows that the screen now says “failed”?</li>
    <li>What happens if the same failure notification arrives twice?</li>
    <li>In production, how many failed exports still show up as “in progress”?</li>
  </ul>
  <p class="source">Sources: <TalkReferencesLink sourceId="r17">Google Research (2024), Resolving Code Review Comments with Machine Learning</TalkReferencesLink> · <TalkReferencesLink sourceId="r18">Gao et al. (2026), On Autopilot? Human–AI Teaming and Review Practices in Open Source</TalkReferencesLink> · <TalkReferencesLink sourceId="r49">Google SRE (2018), Alerting on SLOs</TalkReferencesLink></p>
  <aside class="notes">
    <p>The agent opened the PR. To verify the fix, make a test export fail and open the request on screen. Before the change, it stayed “in progress.” With the fix, it should say “failed.”</p>
    <p>During review, try delivering the same notification again. The request should still say “failed.” That gives the reviewer a concrete case to discuss in the PR.</p>
    <p>After deployment, match failure notifications from the generator to the status the screen reads, using the request ID. Count requests still marked “in progress” after the expected update time. Track that count to see whether the fix reached the person waiting for the report.</p>
    <p>Someone with context still decides whether to accept the change. In production, the on-call engineer confirms impact, authorizes mitigation and checks recovery against the service indicator.</p>
    <p>Evidence</p>
    <p>AI-assisted PRs from contributors who had not previously owned the code showed few explicit signs of review [R18].</p>
    <p>RCACopilot reached up to 0.766 accuracy in classifying the cause category of Microsoft incidents [R31].</p>
    <p>The on-call engineer confirms impact, authorizes mitigation and uses the SLI to check recovery [R49].</p>
    <p>Treat tool output as data. In the Nx package incident, malware instructed AI CLIs to look for secrets [E28].</p>
    <p>A good sign: the review queue stays manageable as generation increases [R18, R28]. The service indicator confirms recovery [R49].</p>
    <p>Refs: R17, R18, R28, R31, R49, E28.</p>
  </aside>
</section>

<section>
  <h2>Measure and improve</h2>
  <p class="label">Three things to measure separately</p>
  <div class="columns">
    <div class="pair">
      <strong>product</strong>
      <p>Does it deliver what the user was promised?</p>
    </div>
    <div class="pair">
      <strong>agent</strong>
      <p>Can it do this kind of task with the expected quality and permissions?</p>
    </div>
    <div class="pair">
      <strong>team</strong>
      <p>Does it take less total effort to ship and maintain changes?</p>
    </div>
  </div>
  <div class="signal">
    <p class="label">A good sign</p>
    <p>Throughput rises while instability and the review queue stay in check.</p>
  </div>
  <p class="source">Sources: <TalkReferencesLink sourceId="r41">Anthropic (2026), Demystifying evals for AI agents</TalkReferencesLink> · <TalkReferencesLink sourceId="r57">Díaz-Villegas et al. (2026), Design Problems, Decisions, and Evidence in Agentic Software Engineering</TalkReferencesLink> · <TalkReferencesLink sourceId="r30">DORA, Software delivery performance metrics</TalkReferencesLink> · <TalkReferencesLink sourceId="v01">Lauren Tan, AI Engineer (2026), All Code Is Slop (Except Mine)</TalkReferencesLink></p>
  <aside class="notes">
    <p>Measure at three levels. Compare versions by changing one component at a time.</p>
    <p>Evidence</p>
    <p>Build a local suite of tasks with known outcomes. Record the expected result before execution [R41].</p>
    <p>pass@k measures at least one success in k attempts. pass^k requires success on all k attempts [R41].</p>
    <p>Across 94 studies, only 19.8% of evaluation records attributed evidence to an individual design decision [R57].</p>
    <p>Track accepted tasks divided by assigned tasks, human minutes including review and rescue work, the review queue and DORA metrics [R27, R30].</p>
    <p>The Grok Bot team reports shipping 11,000 PRs in a month and reverting about 0.5%. They also compared startup, typing and chat-switching performance at release. The revert rate misses bugs fixed in a subsequent PR [V01, 13:32].</p>
    <p>A good sign: higher throughput with no increase in instability or the review queue [R30].</p>
    <p>Refs: R27, R30, R41, R57, V01.</p>
  </aside>
